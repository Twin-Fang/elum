## 1. 한 줄 결론

> **ELUM은 "AI가 행동 카드를 잘 만들어주는 앱"이 아니라, 보호자·지도자가 이미 만들어 둔
> 행동·강화 구조를 보호자가 없는 상황에서도 상기시켜 주는 자립 보조 도구다.**

자문의 무게중심은 **생성 품질이 아니라 수행 동기(강화)와 개인화**에 있었다.
카드를 아무리 잘 만들어도 사용자가 그 행동을 하기 싫으면 하지 않는다.

---

## 2. 자문에서 확인된 핵심 9가지

1. 서비스 대상은 **연령이 아니라 기능 수준**으로 정의한다.
2. 앱의 역할은 **교육이 아니라 상기(remind)와 자립 지원**이다.
3. 행동 단계만으로는 부족하다. **보호자가 설정한 강화(보상)를 함께 보여줘야** 한다.
4. 과제분석은 사용자마다 다르므로 **보호자의 추가·삭제·수정이 핵심 기능**이다.
5. 현재 구조는 행동중재의 **과제분석(Task Analysis)·연쇄(Chaining)** 개념과 연결된다.
6. 개별화는 필요하지만 **온보딩은 가볍게** 유지해야 한다 (보호자 이탈 방지).
7. MVP는 **최소 기능으로 출시하고 실사용 피드백으로 개선**한다.
8. 리포트는 임상 지표가 아니라 **행동 수행률**부터 시작해도 충분하다.
9. 앱이 자립을 만드는 것이 아니다. **오프라인 구조를 디지털로 보조**하는 역할로 정의해야 한다.

## 3. 대상·역할 정의 (변경)

### 3-1. 대상 — 연령이 아니라 기능 수준

생활연령과 발달연령은 다르다. "7~12세 발달장애 아동"으로 한정할 근거가 약하고,
**성인 발달장애인도 기능 수준에 따라 충분히 대상이 된다.**

판단 기준은 다음 4가지다.

- 스마트폰을 어느 정도 사용할 수 있는가
- 그림·글씨 등 시각정보를 이해할 수 있는가
- 행동의 순서(시퀀스)를 이해할 수 있는가
- 행동을 새로 배우기보다 **이미 아는 행동을 상기**할 수 있는 수준인가

**말을 하지 못해도 대상이 될 수 있다.** 언어 표현이 어려워도 그림·글씨·화면·영상·음성은
활용 가능한 경우가 많다. "대화가 가능한 발달장애인"으로 좁히지 않는다.

> **확정 정의**: *행동 카드의 시각정보와 순서를 이해할 수 있는 발달장애인*

### 3-2. 역할 — 교육이 아니라 상기

앱은 행동을 처음부터 가르치지 않는다. 보호자가 곁에서 하던 다음 역할의 일부를 대신한다.

- "이제 이거 해야 해"
- "다음은 이거야"
- "끝나면 이것을 할 수 있어"

최종 목표는 보호자 개입을 점진적으로 줄여 **혼자 일과를 수행**하게 만드는 것이다.

### 3-3. 쓰지 말아야 할 표현

| 금지 | 대체 |
| --- | --- |
| ELUM이 발달장애인의 행동을 교정한다 | 보호자·지도자가 구성한 일상 행동 지원 구조를 디지털로 확장해, 보호자가 없는 상황에서도 사용자가 행동 순서를 확인하고 수행하도록 지원한다 |

## 4. 기능 피드백

### 4-1. 강화(Reinforcement) — 이번 자문의 최대 지적사항

순서만 알려주는 것으로는 행동이 일어나지 않는다.

```text
버스를 타세요 → 버스에서 내리세요 → 회사까지 걸어가세요
```

순서를 알아도 **그 행동을 하기 싫으면 하지 않는다.** 동기를 제공하는 강화 프로그램이 필요하다.

**구조**: 보호자가 보상을 설정 → 앱이 행동 전·중·후에 상기시킨다.
**앱이 보상을 결정하지 않는다.** 결정은 보호자, 앱은 표시·상기만 한다.

보상 예시: 좋아하는 점심 먹기 / 유튜브 10분 / 좋아하는 놀이 / 간식 / 산책

**보상은 가까울수록 좋다.**

| 부적절 (장기) | 적절 (즉각·근접) |
| --- | --- |
| 한 달 동안 잘하면 선물 | 일과를 마치면 간식 |
| 한 학기 잘하면 여행 | 학교에 도착하면 좋아하는 활동 |

### 4-2. 보호자 모드 — 강화 설정 기능

일과 생성 과정에 질문을 추가한다.

> "이 일과를 모두 완료하면 무엇을 할 수 있나요?"
> "자녀가 이 일과를 완료했을 때 제공할 보상을 설정해주세요."

### 4-3. 아동 모드 — 보상 지속 노출

```text
오늘의 목표 / 보상
  ↓
행동 1 → 행동 2 → 행동 3
  ↓
완료 → 보호자가 설정한 보상
```

**수행 중에도 최종 보상을 계속 확인할 수 있어야 한다.** (상단 고정 등)

### 4-4. 보호자 가이드

강화물을 설정하려면 보호자가 강화 개념을 알아야 한다. 긴 전문 교육이 아니라 짧은 안내로 충분하다.

> **보상이란?** 사용자가 행동을 수행할 수 있도록 동기를 주는 것입니다.
> 실제로 좋아하는 활동이나 음식 등을 선택해주세요.

### 4-5. 단계 수는 고정이 아니다 — 개인화가 핵심

모든 사용자에게 고정된 5단계·8단계를 주는 방식은 부적절하다.
어떤 사용자는 버스 이용에서 **타기·내리기 두 단계만** 어려울 수 있다.
이미 혼자 하는 "정류장까지 가기", "교통카드 찍기"까지 매번 카드로 보여줄 필요가 없다.

> 핵심은 **단계 수가 아니라 개인화**다.

### 4-6. AI 결과는 정답이 아니라 초안

```text
AI 자동 생성 → 보호자 검토 → 불필요 단계 삭제 → 필요 단계 추가·수정 → 최종 카드
```

필요한 편집 기능: **삭제 / 추가 / 문구 수정 / 이미지 수정·재생성 / 순서 변경**

### 4-7. 이론적 근거 — 과제분석과 연쇄

- **과제분석(Task Analysis)**: 복잡한 행동을 작은 단계로 나눔 (= 현재 카드 생성)
- **연쇄(Chaining)**: 나눈 단계를 순서대로 연결해 하나의 행동을 완성 (= 현재 카드 순서 수행)

같은 "학교 가기"라도 사용자 A는 5단계, 사용자 B는 2단계면 충분하다.
→ **단계의 추가·삭제·수정이 자유로워야 한다.**

### 4-8. 이미지 추상화 수준

```text
실제 사진 → 사실적인 그림 → 카툰 → 선화 → 기호
```

추상화될수록 이미지와 실제 행동의 관계를 이해하기 어려운 사용자가 생긴다.
ABA 자료가 실물 사진을 많이 쓰는 이유다.

다만 **현재 타겟(스마트폰·그림 이해 가능) 기준에서는 카툰형 이미지도 충분히 사용 가능**하다.
반드시 실물 사진이어야 하는 것은 아니며, **사용자 수준에 맞는 명확한 시각자료**가 중요하다.

### 4-9. 셀프 모델링 (확장)

일반 캐릭터 대신 **사용자 얼굴을 반영한 캐릭터**가 행동하는 이미지를 생성하는 방식.
행동과 자신을 연결하는 데 도움이 될 수 있으나 구현 복잡도가 높아 **MVP 이후 확장**으로 둔다.

### 4-10. 온보딩·MVP는 가볍게

발달장애인 보호자는 이미 돌봄·이동·교육 부담이 크다. 설정이 복잡하면 앱을 쓰지 않는다.

> **개별화는 하되 온보딩은 최대한 가볍게** — 처음엔 최소 정보만, 사용하면서 점진적으로 추가

| 우선 | 후순위 |
| --- | --- |
| 카드 생성 / 보호자 수정·삭제·추가 / 순서 확인 / 완료 체크 / 강화 설정·표시 / 알림 / 간단 리포트 | 복잡한 캐릭터 기능 / 과도한 사용자 분석 / 세분화된 설정 / 복잡한 애니메이션 / 고도 시각효과 |

### 4-11. 리포트는 수행률 중심

단순 시간표보다 **실제 행동 수행 정도**가 의미 있다.

| 날짜 | 완료 단계 | 전체 단계 | 수행률 |
|---|---:|---:|---:|
| 월 | 10 | 10 | 100% |
| 화 | 10 | 10 | 100% |
| 수 | 8 | 10 | 80% |
| 목 | 3 | 10 | 30% |

평소 100%이던 수행률이 30%로 떨어지면 보호자가 **그날의 환경 변화를 점검하는 근거**가 된다.
초기에는 임상 지표 없이 다음 정도면 충분하다 — 수행 여부 / 전체 단계 수 / 완료 단계 수 / 수행률 / 일자별 추이

### 4-12. 내면 조절이 아니라 행동으로 ⚠️

> **"마음을 다스려요", "진정해요" 같은 건 안 된다. 행동으로 해야 한다."**

자폐·지적장애인에게 **내면의 정서 조절을 목표로 제시하는 것은 적절하지 않다.**
기분이 나쁘면 **폰을 던지는 것**이지, 속으로 감정을 다스리는 방식으로 작동하지 않는다.

| 카드가 될 수 없는 것 | 카드가 되는 것 |
| --- | --- |
| 마음을 다스려요 | 조용한 곳으로 가요 |
| 진정해요 | 물을 한 컵 마셔요 |
| 참아요 | 숨을 크게 다섯 번 쉬어요 |

**판단 기준은 하나다 — 눈으로 보고 "했다/안 했다"를 확인할 수 있는가.**
확인할 수 없으면 `했어요!` 버튼을 누를 수 없고, 수행률도 계산할 수 없다.

> 전년도 수상작 토닥이도 같은 구조다 — "진정하기"가 아니라 **"이어폰 끼기", "주먹 쥐었다 펴기 10번",
> "벽 쪽으로 한 걸음 가기"** 처럼 구체적 행동으로 제시한다.

### 4-13. 추천 일과가 사용자 상황과 맞지 않는 문제 ⚠️

소장님이 **직접 겪으신 사례** — 아드님이 **회사에 다니시는데** 앱의 추천 일과에
**"학교에 가요"** 가 떠 있었다.

당시 추천 50개가 **전부 "아이가 ~" 로 시작하고 학교·등교·스쿨버스·선생님 중심**이었다.
성인 발달장애인에게는 첫 화면부터 맞지 않는다.

> 이 지적이 **타겟을 연령이 아니라 기능 수준으로 정의해야 하는 이유**를 가장 구체적으로 보여준다.
> 문서상 정의만 바꾸고 추천 목록을 그대로 두면 실사용에서 같은 문제가 반복된다.

### 4-14. 앱만으로 자립이 만들어지지 않는다

오프라인에서 보호자·교사·지도자가 **행동과 강화 구조를 먼저 만든다.**
앱은 그 구조를 보호자가 없을 때 상기시키는 역할이다. 서비스 소개 문구도 이 선을 지킨다.

## 9. 서비스 방향 한 문장 (개정)

> **보호자가 발달장애인의 일과와 강화물을 설정하면, AI가 이를 이해하기 쉬운 작은 행동 단계와
> 시각자료로 구성하고, 사용자가 보호자의 지속적인 개입 없이도 다음 행동과 최종 목표를 확인하며
> 일과를 수행할 수 있도록 지원하는 자립 보조 서비스**

```text
AI 생성 → 개인화된 행동 지원 → 강화 상기 → 보호자 개입 감소 → 자립 지원
```
