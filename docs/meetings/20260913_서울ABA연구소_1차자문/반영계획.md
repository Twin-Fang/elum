## C. 데이터 모델 변경 (B1 선행)

현재 `Routine` 에는 보상 개념이 전혀 없다.

```java
// server/.../routine/infrastructure/entity/Routine.java — 현재
private String rawInputText;
private String sanitizedInputText;
private String title;
private LocalDateTime scheduledAt;
private RoutineStatus status;
private List<RoutineStep> steps;
// 보상 관련 필드 없음
```

**추가 검토 항목**

| 항목 | 논점 |
| --- | --- |
| 보상 저장 위치 | `Routine` 필드로 둘지, 별도 `Reward` 엔티티로 뺄지 (일과별 1개면 필드로 충분) |
| 보상 표현 | 자유 텍스트 vs 프리셋(간식·유튜브·놀이·산책) + 직접 입력 — **보호자 입력 부담**을 고려하면 프리셋 우선 |
| 보상 이미지 | 카드처럼 이미지가 필요한가 (아동이 글을 못 읽을 수 있음) |
| DLP 적용 | 보상 텍스트도 보호자 자유 입력이다. **DLP 마스킹 대상에 포함해야 한다** |

> ⚠️ **보상 입력도 보호자의 자유 입력이다.** 일과 입력문과 동일하게 DLP를 거쳐야
> 서비스 원칙 2번("보호자 입력 원문을 LLM에 그대로 보내지 않는다")이 유지된다.
> 보상 텍스트를 AI 프롬프트에 넣을 계획이라면 설계 단계에서 반드시 확인한다.

## E. 처리 순서

```text
A (문서 정합)  →  B1·C (데이터 모델)  →  B2·B4 (강화 UI)  →  B3·B5 (개인화)  →  B6~B9 (P1)
```

**A를 먼저 하는 이유** — 문서와 코드가 다른 서비스를 설명하는 상태가 길어지면,
다음 미팅에서 "무엇을 기준으로 피드백받아야 하는지"가 흐려진다.

**B1·C를 B2보다 먼저 하는 이유** — 보상 저장 구조가 정해지지 않으면 화면을 만들어도 붙일 곳이 없다.
