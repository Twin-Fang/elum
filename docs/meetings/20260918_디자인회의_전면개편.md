## 1. 결정한 것 ✅

| # | 결정 | 근거 |
| :-: | --- | --- |
| 1 | **OAuth 4종 전부 유지** (카카오·네이버·Google·Apple) | 이미 심사 중인 앱이다. 수단을 지우면 **그 수단으로 가입한 계정이 잠긴다.** Apple은 iOS 심사 필수 |
| 2 | **도움 목표 4개 문구 현행 유지** | 바꾸려던 의도는 있었으나 **어디에도 기록이 없다** (§3-1) |
| 3 | **보상 설정은 카드 검토 다음** (`4/4`) | 카드를 다 보고 정하는 편이 맥락이 잡힌다. **9/13 명세(카드 생성 앞 `3/4`)를 뒤집는다** |
| 4 | **카드 추가·순서 변경·알림을 이번 범위에 포함** | **9/13의 P1 보류를 뒤집는다** |
| 5 | **보호자 홈은 4구역** — 오늘 일과 / 진행 중 / 임시저장 / 최근 일과 | **9/13의 "임시저장은 배지" 안을 뒤집는다** |
| 6 | 🔴 **카드 그림을 다시 만들지 않는다** | **AI 이미지 생성 비용.** 이미 만들어진 카드의 그림 교체를 지원하지 않는다 |
| 7 | **스플래시 `시작하기` 버튼 제거** → 로그인 버튼을 바로 노출 | 다음에 뭐가 나올지 말해 주지 않는다. 누를 것이 하나뿐인 화면은 그 자체로 잡초다 |
| 8 | **말투는 토스 라이팅 원칙을 따른다** | 해요체·능동형·긍정형. 8원칙 적용 |
| 9 | **타겟을 나이로 명시한다** — 보호자 **50대** · 당사자 **20대** | 한 앱에 성격이 다른 두 사용자가 있다 |
| 10 | 🔴 **사용자를 `이룸이`라고 부른다** — `아이`·`아동`을 안 쓴다 | 20대 당사자가 자기 휴대폰에서 이 앱을 연다 |
| 11 | 역할 선택 제목은 **`서비스를 누가 사용하나요?`** | `이 휴대폰`은 누구 휴대폰인지 헷갈린다 |
| 12 | 역할 선택 선택지는 **보호자 / 이룸이** · 여기서 `연결 번호`를 말하지 않는다 | 번호를 받은 적 없는 사람에게 코드 얘기를 하면 막힌다 |
| 13 | `코드` 대신 **`연결 번호`** | 50대·20대 둘 다에게 `번호`가 쉽다 |
| 14 | **카드 편집을 목록 화면으로 분리** | 캐러셀에 버튼 4개를 늘어놓는 앱은 없다 |
| 15 | **그림 교체 기능을 만들지 않고, 화면에서 언급도 안 한다** | 없는 기능을 설명하면 없다는 사실만 커 보인다 |
| 16 | **버튼에는 바로 다음에 올 화면 이름을 쓴다** — 검토는 `보상 정하기`, 보상은 `이룸이에게 보내기` | 검토 화면에서는 아직 보내지 않는다 |

> 3·4·5는 **9/13에 정한 것을 뒤집은 결정이다.** 메모가 더 최신이므로 메모를 따랐다.
> 10~15는 **2차 회의(9/18)에서 추가로 결정됐다.**

### 10번이 가장 넓게 퍼진다

`아이` 표현이 **화면 문구 12곳 + 서버 AI 프롬프트 3곳**에 있다.
서버 프롬프트는 AI가 만드는 카드 문구의 말투를 정하므로, 고치지 않으면
*"아이에게 말하듯"* 만들어진 문장이 20대 당사자에게 그대로 간다.

⚠️ **두 곳은 건드리지 않는다.**

| 곳 | 왜 |
| --- | --- |
| `consent_documents.dart:63` 법정대리인 동의 | 법적 효력이 있는 문장이다 |
| `PromptDefaults.java:38` DLP 이름 판별 규칙 | `"아이"는 이름이 아니다`를 지우면 마스킹이 오작동한다 |

> 보호자는 실제로 "우리 아이가…"라고 입력한다.
> **입력으로 들어오는 `아이`는 그대로 받고, 화면에 나가는 `아이`만 바꾼다.**

### 14번 — 왜 버튼을 늘어놓지 않기로 했나

처음 안은 검토 화면에 `고치기` `삭제` `+ 카드 추가` `⇅ 순서` 네 버튼을 두는 것이었다.
**그렇게 만든 앱이 없다.** 캐러셀은 보는 뷰이고, 순서·삭제·추가는 목록에서 해야 손에 잡힌다.

```
검토 화면          →   카드 편집 목록
[ 카드 편집 ]           ☰ 끌어서 순서
[ 보상 정하기 ]         행 탭 → 고치기 시트 (삭제도 여기)
                        + 카드 추가 (점선 행)
```

검토 화면의 결정은 둘뿐이다 — **고칠까, 넘어갈까.**

### 16번 — 버튼에는 "바로 다음에 올 것"을 쓴다

처음 안은 검토 화면 CTA를 `이룸이에게 보내기`로 두었다. **그런데 이 화면 다음은 보상 정하기다.**
여기서 보내지 않는다.

| 화면 | CTA | 왜 |
| --- | --- | --- |
| 카드 검토 (3/4) | **`보상 정하기`** | 다음 화면 이름 그대로 |
| 보상 정하기 (4/4) | **`이룸이에게 보내기`** | **여기가 실제로 보내는 자리다** |

같은 이유로 나갈 때 팝업도 고쳤다. `아직 안 보냈어요` → **`아직 저장하지 않았어요`**.
검토 화면에서 나가는 사람은 **보낸 적이 없다.** 저장이 안 된 게 문제지 안 보낸 게 문제가 아니다.

## 2. 논의 내용

### 2-1. "다 수정해야 한다"는 부담 — 실제로는 8개 화면을 손대지 않는다

디자이너가 개편 범위를 전부 새로 그리는 것으로 받아들였다.
화면 단위로 펼쳐 보니 **이미 구현돼 손댈 필요 없는 화면이 8개**였다.

```
메모 7개 항목  →  화면 18개
                  ├ 손 안 댐 8  (로그인·약관·이름·캐릭터·PIN·일과입력·AI질문·별화면)
                  ├ 새로 그림 7
                  └ 고침 7
```

**형태를 처음부터 잡아야 하는 것은 5개뿐이다** — QR 발급, 보상 설정 레이아웃,
상단 고정 보상 바, 순서 변경 리스트, **그림 없는 카드**.
나머지는 기존 컴포넌트를 재사용한다 (코드 입력 = PIN 화면, 보상 칩 = 목표 칩).

### 2-2. 9/13 명세와 충돌 5건 — 메모를 기준으로 잡았다

| 쟁점 | 9/13 명세 | 이번 메모 | 채택 |
| --- | --- | --- | :-: |
| 보상 설정 위치 | 카드 생성 앞 `3/4` | 카드 검토 뒤 `4/4` | **메모** |
| 카드 추가·순서 | P1 (본선 10/28) | 이번 범위 | **메모** |
| 임시저장 | `오늘` 안의 배지 | 별도 섹션 | **메모** |
| 홈 섹션 | 3구역 | 4구역 | **메모** |
| 추천 일과 | 유지 | 언급 없음 | **유지** (삭제 지시가 아니라 생략으로 봄) |

### 2-3. 🔴 카드 그림 비용 — 디자인이 하나 늘었다

"이미 만든 카드의 그림은 안 바꾼다"가 **빼는 결정이 아니라 더하는 결정**이었다.

| 동작 | 그림 | 따라오는 디자인 |
| --- | --- | --- |
| 문구 수정 | 유지 | 수정 시트에서 **그림 교체 버튼을 뺀다** |
| **카드 추가** | **없다** | 🎨 **그림 없는 카드를 새로 그려야 한다** |

추가한 카드는 캐러셀에서 다른 카드와 나란히 넘어간다. 형태가 다르면 눈에 띈다.
**기본 그림 1종(A안)** 으로 정했다 — 내용을 암시하지 않는 중립적인 그림.

> **에셋 중 가장 급하다.** 보상 프리셋은 이모지로 버틸 수 있지만 이쪽은 대체할 것이 없다.

### 2-4. 50대 보호자를 가르치되, 화면을 글로 채우지 않는다

보호자는 50대고 `보상`·`임시저장`·`휴대폰 연결`은 처음 보는 개념이다.
그렇다고 설명을 늘리면 아무도 안 읽는다. **두 요구가 부딪쳤다.**

**결론 — 본문은 한 줄, 설명은 시트로 접는다.**

```
❌ 화면에 5줄 설명            ✅ 한 줄 + "왜 정하나요? ›"
   아무도 안 읽는다              읽을 사람만 읽는다
```

보상 안내 시트가 이 패턴의 기준 사례다. 낯선 개념마다 같은 방식을 쓴다.

### 2-5. 목표 4개 문구를 찾지 못했다

메모에 *"선택지 바뀌어야 하는데 명세 어디에 적어놨다"* 고 되어 있었다.

| 찾아본 곳 | 결과 |
| --- | :-: |
| `docs/` 명세 25건 | 없음 |
| 회의록 4건 | 없음 |
| projectops 리포트 전수 | 없음 |
| `client/lib` 전수 | 없음 |
| **과거 대화 아카이브** | 없음 |

**구두로만 언급되고 기록되지 않았다.** 현행 유지로 확정했다.

### 2-6. 화면에서 찾은 실제 결함

문구를 안 바꿔도 지금 렌더링이 깨져 있다.

| # | 문제 | 원인 |
| :-: | --- | --- |
| 1 | 목표 4번 칩에서 `요` 한 글자만 둘째 줄로 떨어진다 | 칩 높이 **68 고정** · 텍스트에 줄 수 제한 없음 |
| 2 | 목표 3번 아이콘만 무채색 | 나머지 3개는 컬러 |
| 3 | **시스템 글자 확대에 대응 안 되어 있다** | `textScaler` 처리 없음 |

> 1번과 3번은 같은 뿌리다. **50대 보호자가 글자 크기를 키우면 고정 높이 컴포넌트가 깨진다.**

## 부록 — 구두 전달 메모 원본

> 정리본은 해석이 섞이므로 원본을 남긴다.

```
1. 홈화면 (싹다 OAuth: 구글, 네이버, 카카오, 애플 > 알아서 줄이셈)
2. 약관화면
3. 보호자입니까, 사용자입니까
   보호자임 > 사용자 QR,코드 연결하겠습니까 (#158)
4. 4가지 고르잖아 바뀌어야함
   (선택지 바뀌어야되는데 : 명세어디에 적어놨는데 확인해봄)
4. 보상 설정 화면
   (일과입력 > AI질문 > 카드생성 > 카드검토 > 보상)
   건너뛰기 있어야되고 / 직접입력 / 최근 보상 정보
5. 홈화면
   오른쪽위에 설정 아이콘 > 회원탈퇴, 로그아웃, 연결코드생성, 알림
   안녕하세요 / 새로운 일과만들기 / 오늘 일과
   === 진행중(보상)
   수정을 눌러서 그화면에서 생성 (이거가 필요하다함)
   === 임시저장 (보상)
   === 최근 일과
6. 행동 카드 수정
   카드 삭제, 추가, 순서변경
7. 사용자화면
   > 보상표시, 마지막에 다 마쳤을때 어떤식으로 보여주느냐
```

**추가 전달 (구두)**
