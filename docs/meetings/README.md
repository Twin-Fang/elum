## 폴더 규칙

```
docs/meetings/
├── README.md                          # 이 파일 — 인덱스
├── _template/회의록.md                # 새 미팅 시작할 때 복사해서 쓴다
└── YYYYMMDD_기관명_N차자문/
    ├── README.md                      # 회의록 본문 (폴더를 열면 바로 보인다)
    ├── 반영계획.md                     # 문서 수정 · 이슈 · 모델 변경으로 쪼갠 실행 계획
    └── raw/                           # 가공 전 원본 — 녹취 요약, 받은 자료, 사진
```

- 폴더명은 `YYYYMMDD_기관명_N차자문` — `docs/projectops/` 의 날짜 규칙과 맞춘다.
- 회의록 본문은 항상 **`README.md`** 로 둔다. GitHub에서 폴더만 눌러도 바로 읽힌다.
- 녹취·요약 **원본은 반드시 `raw/` 에 그대로 남긴다.** 정리본은 해석이 섞이므로,
  나중에 "그때 소장님이 정확히 뭐라고 했더라"를 확인할 원본이 따로 있어야 한다.

## 회의록에 반드시 들어갈 것

자문 내용을 그대로 옮겨 적기만 하면 **한 달 뒤에 아무것도 하지 않은 문서**가 된다.
아래 3개가 있어야 회의록이 실제로 작동한다.

| 항목 | 이유 |
| --- | --- |
| **기존 기획과 충돌하는 지점** | 어떤 문서의 어떤 문장을 고쳐야 하는지 표로 특정한다 |
| **현재 구현 대비 갭** | 코드를 확인하고 근거 파일 경로를 적는다. "있을 것 같다"로 적지 않는다 |
| **다음 미팅으로 넘길 것** | 결론이 안 난 것과 구현 후 재확인할 것을 분리해 남긴다 |
| **반영계획.md** | 위 세 가지를 문서 수정·이슈·모델 변경으로 쪼갠 실행 체크리스트 |

> 회의록을 쓴 뒤에는 **기획 문서 수정 → 이슈 등록**까지 이어져야 한다.
> 회의록만 쌓이고 문서·코드가 그대로면 두 기록이 서로 다른 서비스를 설명하게 된다.
