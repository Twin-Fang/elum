# 관리자 페이지 UX 재설계

## 의도와 이유
관리자가 "지금 실제로 어떻게 적용돼 있나"를 한눈에 못 보고, 검색·정렬·필터가 화면마다 제각각이거나 없다.
실증 하루 전, Free 광고 제거를 켰는데 관리자 화면으로는 켜졌는지 확인할 수 없어 DB를 직접 열었다.
목표는 **현재 상태가 먼저 보이고, 어디서든 같은 방식으로 찾고 거르고 정렬하는** 관리자 페이지다.

## 목표 / 비목표 / 안티목표
- 목표
  - 현재 적용 상태를 첫 화면에서 본다 (기본값과 다른 설정, Free/Pro 비교, 켜진 이벤트·점검).
  - 모든 목록 화면이 같은 검색·필터·정렬·페이지 규칙을 쓴다 (기본 정렬 최근 변경순).
  - 모든 설정·콘텐츠 행에 마지막 변경 시각과 변경자를 보인다. 변경 이력은 한 번에 갈 수 있다.
  - 반복 코드(페이저, 필터 바, 날짜 표기, PAGE_SIZE)를 공통 지점 하나로 모은다.
- 비목표: 역할(RBAC) 분리, 새 JS 프레임워크 도입, 관리자 API 계약 변경, 모바일 앱 변경.
- 안티목표: 화면을 바꾸다 기존 저장·권한 동작이 달라지는 것. "AI스러운" 장식 카드·불필요한 안내문 추가.

## 제약
- 스택 유지: Spring MVC + Thymeleaf + daisyUI + 바닐라 JS. 서버 렌더링 + 얇은 JS.
- 기존 admin 컨트롤러·URL 유지(쿼리 파라미터 추가만). 세션 formLogin 유지.
- 설정 값은 서버 캐시 30초, 변경은 `system_config_history` 에 남는다 (유지).
- `server/CLAUDE.md` 규칙 준수. 변경 있는 컨트롤러는 `@JsonErrorResponse` 등 기존 규칙 그대로.

## 결정한 것 (사용자 승인: 추천안 + UX 우선)
1. **시스템 설정은 "표 중심 + 상단 요약 + Free/Pro 비교"** (시안 A + B 요약).
   - 상단 "지금 적용 중" 요약: 기본값과 다른 설정 수·목록, 켜진 이벤트·점검, Free 광고 제거 등 핵심 토글 현재값.
   - Free/Pro 비교 표: 같은 항목을 두 열로(현재 값, 기본값과 다르면 강조).
   - 전체 설정 표: 설정(이름+키), 현재 값, 기본값, 마지막 변경(시각·변경자·사유). 열 클릭 정렬, 기본 최근 변경순.
   - 검색은 이름·키·값·설명·그룹·변경자까지. 필터 칩: 전체, 기본값과 다름, 오늘 변경, 그룹들.
   - 행 클릭 → 오른쪽 패널에서 수정, 해당 키 변경 이력(키별), 저장 즉시 행 갱신(배지·값·시각), 결과 토스트는 행 근처.
   - 날짜·시간 값은 날짜 선택기, 불리언은 토글. 비밀값은 값 노출 없이 "설정됨"과 변경 시각만.
   - 변경 이력 화면: 키·변경자·기간 필터와 페이지, 건수 제한 해제.
2. **공통 기반을 먼저 만든다** (모든 화면이 쓸 것): 페이저 fragment, 필터 바 fragment(검색+칩+정렬), 날짜 포맷 유틸 하나, 목록 기본 PAGE_SIZE 상수 하나, 마지막 변경 표시 컴포넌트.
3. **목록 화면 규칙 통일**: 회원(정렬 선택, 요금제 열·필터, 마지막 변경), 일과(상태 필터, 회원 링크), 공지(검색·페이징 추가), 의견(처리 상태·필터), 모니터링(기간·회원 필터), 프롬프트(수정자·시각 포맷), 약관(유지, 표기만 통일).
4. **대시보드**: 요금제 분포(Free/Pro), 지금 적용 중 설정 요약, 숫자 카드를 해당 목록 링크로.
5. **내비게이션**: 사이드바를 그룹화(운영: 회원·일과·크레딧·의견 / 콘텐츠: 공지·약관·프롬프트 / 시스템: 설정·모니터링·로그), 오류 배지 유지.
6. **모바일**: 모든 표는 가로 스크롤 보장(`overflow-x-auto` 누락 화면 보강), 표 위 필터 바는 줄바꿈.

7. **확장성·운영 자립 (사용자 요청 2026-10-18: 확장성, 최적화, DB 직접 조회 없이 운영)**
   - **선언형 목록**: 화면마다 템플릿을 새로 짜지 않는다. 목록 정의(열, 검색 대상, 필터, 정렬 키, 기본 정렬, 행 링크)를 정의 객체 하나로 선언하면 공통 목록 템플릿이 표·필터 바·페이저를 그린다. 새 관리 화면은 정의 객체 하나 추가로 같은 UX를 얻는다.
   - **운영 작업을 화면에서**: 운영자가 DB 를 열지 않아도 되게 한다. 회원 요금제 부여·회수(기간·사유), 설정 변경, 신규가입 이벤트, 점검 모드를 화면에서 하고, 모든 변경은 변경 전후·변경자·사유가 이력에 남는다(감사). 이번 실증에서 DB 를 직접 고친 일이 다시 필요 없게 하는 것이 기준이다.
   - **최적화**: 목록은 서버 페이징(고정 상한), 정렬·검색 대상 컬럼 인덱스 점검, N+1 금지(목록 쿼리 한 번으로 연관값 포함), 설정 조회는 기존 30초 캐시 유지, 대시보드 집계는 짧은 캐시(예: 60초)로 매 요청 집계 쿼리를 막는다. 큰 목록(모니터링·로그)은 기간 필터 기본값을 둔다.
   - **지속 가능성**: 규칙 테스트(공통 목록 정의 사용, PAGE_SIZE 단일 원본, 새 admin 목록이 정의 없이 추가되지 않음)로 봉인한다.

## 빌더에게 맡기는 것 (내 판단, 표시)
- 구체 색·간격·아이콘은 기존 daisyUI 테마를 따른다 (내 판단).
- 정렬·필터의 서버/클라 처리 구분: 데이터가 한 페이지에 다 있는 설정 화면은 클라이언트에서, 페이징되는 목록은 서버 쿼리 파라미터로 (내 판단).
- 설정 "마지막 변경자·시각·사유"는 기존 `system_config_history` 의 최신 행에서 가져온다 (엔티티에 컬럼 추가 없음, 내 판단).
- 이슈는 영역별로 쪼갠다: ① 공통 기반 ② 시스템 설정 ③ 회원·요금제 ④ 일과 ⑤ 공지·의견 ⑥ 모니터링·로그·프롬프트·약관 표기 ⑦ 대시보드·내비게이션·모바일. ①이 먼저, 나머지는 ① 후 병렬.

## 빌더 점검 후 확정 (내 판단은 [내 판단] 표시)
- 신규가입 PRO 이벤트는 이미 develop 에 있다(#746/#747): ConfigKey 4개(SIGNUP_PRO_EVENT_ENABLED/START_AT/END_AT/GRANT_DAYS)와 `planOf` 판정. "켜진 이벤트"는 ENABLED=true 이고 현재가 [START,END] 안인 것.
- "기본값과 다름" 기준: yml 을 포함한 유효 기본값과 비교, 값이 비어 기본값으로 폴백되면 "같음" [내 판단].
- 설정 마지막 변경: 키별 최신 이력 행을 group-by 한 쿼리 한 번으로 가져온다(N+1 금지). 이력이 없는 키는 "기본 설정 (변경 이력 없음)" [내 판단].
- 선언형 목록 정의는 회원·일과·공지·의견·모니터링·프롬프트·약관에 적용한다. 크레딧(탭형)과 서버 로그(파일 tail)는 공통 스타일·페이저만 쓰고 정의 객체에서는 제외 [내 판단].
- 대시보드 60초 캐시는 기존 캐시 인프라를 쓰고 인스턴스별이어도 좋다(60초 어긋남 허용, 운영은 Blue/Green 으로 한 번에 한 인스턴스) [내 판단].
- 모니터링·서버 로그 기간 필터 기본값은 최근 7일 [내 판단].
- 변경자: 공지(`updatedBy`)·약관(`changedBy`)은 이미 있다. 프롬프트 이력에 `changedBy` 가 없어 추가한다. 요금제 부여·회수는 이력이 없어 `subscription_history` 테이블을 새로 만든다. 의견 처리 상태 컬럼을 추가한다. 이 셋은 DB 마이그레이션이라 사용자 승인이 필요하다(아래 "사용자 확인").

## 사용자 확인 (결과에 영향)
- DB 마이그레이션(Flyway, 추가 전용: 새 테이블 1개 + 컬럼 2개, 기존 데이터 변경 없음) 허용 여부.

## 하지 않는 것
- 역할 분리, 새 프레임워크, 새 의존성, 공개 API 변경, 앱 변경.
- 기존 데이터 마이그레이션(마지막 변경은 이력 테이블 조회로 해결).

## 테스트 (실패 시나리오 → 층)
- 정렬·필터·검색이 서버 쿼리와 어긋남 → 서비스 단위 테스트(파라미터별 결과).
- 설정 저장 후 화면과 DB 불일치 → 컨트롤러 슬라이스 테스트(저장 응답에 갱신 값·시각 포함).
- 공통 fragment 도입 후 기존 화면 깨짐 → Thymeleaf 렌더 스모크 테스트(화면별 200 + 핵심 요소).
- 새 목록이 공통 규칙을 우회 → 소스 스캔 규칙 테스트(공통 PAGE_SIZE·페이저 fragment 사용).
- 실제 화면 확인: 로컬 서버 기동 후 브라우저로 화면별 캡처(데스크톱·모바일 폭).
