# 다중 보호자 — 이룸이 한 명에 보호자 여럿

> 상태: 설계 확정 (2026-09-23, 사용자 확인) · 구현 전
> 단계 이슈: **#360** 1단계 구조 · **#361** 2단계 초대 API · **#362** 2단계 앱 · **#363** 3단계 이룸이 폰 · **#364** 4단계 V23 · **#365** 초대 링크(일감) · **#366** 개인정보처리방침
> 관련: #158 (계정·프로필 분리) · #198 19번 (이룸이 폰 설정) · #200 (이룸이 휴대폰 연결) · #354 (보호자 암호) · #355 (암호 없는 휴대폰의 보호자 화면 진입) · #359 (이룸이 폰 토큰 갱신 권한)

## 1. 왜 바꾸나

이룸이는 **여러 사람에게서** 일과를 받는다. 엄마와 아빠가 따로 만들고, 센터 복지사도 만든다.
지금은 이룸이(프로필)가 **보호자 계정 하나에만** 붙는다 (`profile.member_id` 단일 외래키).
그래서 두 번째 보호자가 붙을 자리가 없고, 한 사람이 탈퇴하면 그 계정 밑의 이룸이와 일과가
통째로 사라진다.

코드도 이미 이 확장을 전제로 주석을 달아 두었다 — `Profile.java` "형제가 있거나 기관에서 여러
이용자를 지원하는 경우", `Routine.java` "같은 당사자를 보호자와 기관이 함께 지원할 때",
`requireProfile` "프로필이 여럿이 되면 호출부가 어느 프로필인지 명시하게 바꾼다".
**스키마만 아직 따라오지 않았다.**

## 2. 확정한 것 (2026-09-23)

| 쟁점 | 결정 |
|---|---|
| 이룸이 신원 | **계정 없는 독립 주체.** 로그인하지 않는다. 이룸이 휴대폰은 지금처럼 연결 암호로 붙는다 |
| 역할 | **윗사람이 없다.** 연결된 보호자는 모두 동등하다. 보호자/복지사 구분은 표시용 값으로만 둔다 |
| 일과 | 연결된 보호자는 **모두 본다.** 승인·수정·삭제는 **만든 사람만** |
| 이룸이 정보 (이름·캐릭터·도움 목표) | 연결된 보호자 **누구나** 바꾼다. 마지막에 바꾼 값이 남는다 |
| 보호자가 나가면 | **그 사람이 준 일과만** 사라진다. 다른 보호자의 일과와 이룸이는 그대로 |
| 마지막 보호자가 나가면 | 이룸이도 지운다 (돌볼 사람이 없다) |
| 별 | **남긴다.** 이룸이가 해낸 것이다 |
| 요금제 | **만드는 사람 기준.** 지금 구조(계정 단위 구독·한도) 그대로 |
| 초대 | **초대 코드**로 먼저 한다. 링크 공유는 일감으로만 올려 둔다 |

**원칙 하나로 요약하면** — *한 사람이 나가면 자기 것만 지운다.* 그래서 탈퇴·나가기가 서로
충돌하지 않는다.

## 4. 목표 구조

### 4-1. 데이터

```
member (보호자 계정) ──< profile_guardian >── profile (이룸이)
                          kind: GUARDIAN | CAREGIVER   ──< routine (created_by → member)
                          joined_at                    ──< device_link (이룸이 폰, profile_id 필수)
                                                       ──< profile_invite (초대 코드)
```

| 표 | 바뀌는 것 |
|---|---|
| (참고) | 아래 NOT NULL·삭제는 되돌리기 때문에 V22·V23 두 번에 나눠 건다 — 5장 |
| `profile_guardian` 🆕 | `id`, `profile_id` FK, `member_id` FK, `kind`(표시용), `joined_at`, `UNIQUE(profile_id, member_id)` |
| `routine` | `created_by VARCHAR(255) REFERENCES member(id)` 추가. 기존 행은 그 프로필의 보호자로 채운다 |
| `profile_invite` 🆕 | `device_link`와 같은 모양 — `code_hash`, `profile_id`, `issued_by`, `expires_at`, `redeemed_by`, `redeemed_at`, `revoked_at`, `failed_attempts` |
| `profile.member_id` | V22에서 NULL 허용으로 바꾸고 **V23(다음 배포)에서 지운다.** 그 사이에는 "옛 서버 호환용 대표 보호자"로만 쓴다 — 새 코드는 읽지 않고, 가입 때 채우고, 그 보호자가 나가면 남은 보호자 중 가장 먼저 합류한 사람으로 바꾼다 |
| `device_link.profile_id` | 이미 모든 행에 값이 있다(운영 0건 NULL). NOT NULL은 V23에서 건다 |

`kind`는 권한에 쓰지 않는다. 화면에서 "센터 선생님"처럼 부르기 위한 값이다. 권한 차이가
필요해지면 그때 이 값을 근거로 더한다.

### 4-2. 권한 — 서버 한 곳에서 판단한다

새 판단자 `ProfileAccess`(가칭)가 "이 요청자가 이 이룸이에 무엇을 할 수 있나"를 한 곳에서 답한다.
`getOwnedRoutine`의 14곳과 `requireProfile`의 19곳이 이것을 거친다.

| 동작 | 보호자 (연결됨) | 보호자 (연결 안 됨) | 이룸이 폰 |
|---|---|---|---|
| 이룸이 정보·모든 일과 보기 | ✅ | ❌ 403 | ✅ (연결된 이룸이만) |
| 이룸이 정보 수정 | ✅ | ❌ | ❌ |
| 일과 만들기 | ✅ (`created_by`=자기) | ❌ | ❌ |
| 일과 승인·수정·삭제·보상 수정 | **만든 사람만** | ❌ | ❌ |
| 일과 순서 (목록 전체) | ✅ | ❌ | ❌ |
| 단계 체크·해제·진행 | ✅ | ❌ | ✅ |
| 초대 코드 발급 | ✅ | ❌ | ❌ |
| 이룸이 폰 연결 암호 발급·끊기 | ✅ | ❌ | ❌ |
| 이 이룸이에서 나가기 | ✅ (자기만) | — | ❌ |

거절은 403과 에러 코드(`PROFILE_ACCESS_DENIED`, `ROUTINE_NOT_CREATOR` 등 — 이름은 구현 때
`ErrorCode` 관례에 맞춘다). 새 도메인 패키지를 만들면 `GlobalExceptionHandler`의 basePackages
화이트리스트에 더한다 (빠뜨리면 403이어야 할 것이 500으로 나간다 — QA 기록의 함정).

### 4-3. 나가기 · 탈퇴 · 로그아웃

| 누가 · 무엇을 | 지워지는 것 | 남는 것 |
|---|---|---|
| 보호자가 **한 이룸이에서 나가기** | 그 관계 · 그 사람이 만든 그 이룸이의 일과(단계·그림 포함) · 그 사람이 발급한 그 이룸이의 폰 연결과 세션 · 그 사람이 발급한 초대 코드 | 이룸이 · 다른 보호자의 일과 · **별** |
| 위에서 **마지막 보호자**였다면 | 이룸이(프로필·도움 목표) · 남은 폰 연결과 세션 · 남은 초대 코드 | — |
| **회원 탈퇴** | 연결된 모든 이룸이에서 "나가기"를 한 뒤, 기존 순서대로 계정을 지운다(소셜 신원·세션·구독·AI 호출 기록 식별자 분리) | 다른 보호자가 있는 이룸이와 그들의 일과 |
| **로그아웃** | **그 기기의 세션만** | 다른 기기(다른 보호자 폰·이룸이 폰)의 세션 |

- 모든 삭제는 **한 트랜잭션**이다. 중간에 실패하면 전부 되돌린다.
- 이룸이 폰 연결은 연결해 준 보호자에게 묶인다. 그 보호자가 나가면 그 폰은 끊기고,
  남은 보호자가 새 연결 암호로 다시 붙인다. (연결을 다른 보호자에게 자동으로 넘기는 것은
  토큰의 `sub`와 세션 소유까지 옮겨야 해서 하지 않는다.)
- 별은 `profile.total_stars`에 이미 쌓여 있으므로 일과를 지워도 줄이지 않는다.
  (지금 `deleteStep`은 완료된 카드를 지우면 별을 1 뺀다 — **보호자가 스스로 카드를 지울 때**의
  동작이라 그대로 두고, 나가기에 의한 삭제에서는 빼지 않는다.)

### 4-4. 한 보호자가 이룸이 여럿 (복지사)

- 서버 API는 선택 헤더 **`X-Profile-Id`**를 받는다. 없으면 지금처럼 "연결된 이룸이 중 가장 먼저
  합류한 이룸이"를 쓴다. **그래서 1단계에서 앱은 바뀌지 않는다.**
- 헤더의 이룸이에 연결돼 있지 않으면 403.
- `/api/member/me`는 지금 모양(계정 + 기본 이룸이)을 유지하고, 연결된 이룸이 목록
  `profiles: [{id, nickname, character}]`를 더한다 (앱이 모르는 필드는 무시한다).
- 가입할 때 빈 이룸이를 자동으로 만드는 동작은 유지한다. **초대 코드로 합류한 사람이 온보딩을
  하지 않은 빈 이룸이만 갖고 있다면 그 빈 이룸이는 지운다** (이름이 없고 일과가 0건인 것).

### 4-5. 이룸이 휴대폰

- 이룸이 폰 토큰의 요청은 `linkId → device_link.profile_id`로 이룸이를 찾는다.
  "보호자의 첫 이룸이"를 쓰지 않는다. (#359가 갱신 때 `linkId`를 이어 주게 고쳤으므로 가능하다.)
- 이룸이 폰은 그 이룸이에 연결된 **모든 보호자의 일과**를 한데 보여준다 (조회가 이룸이 기준이므로
  따로 할 일은 없다).
- #198 19번(이룸이 폰 상단 바·설정)과 명세 §8-5(보호자가 연결 끊기)는 3단계에서 이 구조 위에
  다시 설계한다.

### 4-6. 초대 코드

- 연결된 보호자가 발급한다. 6자리, 10분, 5번 틀리면 폐기 — `DeviceLinkService`의 발급·검증을
  공통 부품으로 떼어 함께 쓴다 (해시 저장, 헷갈리는 글자 제외 규칙 그대로).
- 코드를 넣은 보호자는 그 이룸이에 `kind=GUARDIAN`으로 붙는다 (복지사 표시는 붙은 뒤 바꾼다).
- 이미 연결된 사람이 넣으면 409. 자기 코드를 자기가 넣어도 409.
- 링크 공유는 **일감으로만** 올린다 (딥링크·설치 전 처리가 필요하다).

## 5. 마이그레이션

**늘리고 → 옮기고 → 줄인다.** 운영 서버가 하나뿐이고 비공개 테스트 앱이 옛 API를 부르므로
한 번에 바꾸지 않는다.

### V22 — 늘리고 옮긴다 (1단계 배포)

```sql
CREATE TABLE profile_guardian (
    id         VARCHAR(255) PRIMARY KEY,
    profile_id VARCHAR(255) NOT NULL REFERENCES profile (id),
    member_id  VARCHAR(255) NOT NULL REFERENCES member (id),
    kind       VARCHAR(30)  NOT NULL DEFAULT 'GUARDIAN',
    joined_at  TIMESTAMP    NOT NULL,
    created_at TIMESTAMP, updated_at TIMESTAMP,
    CONSTRAINT uk_profile_guardian UNIQUE (profile_id, member_id)
);
-- 지금의 1:1을 그대로 관계로 옮긴다
INSERT INTO profile_guardian (id, profile_id, member_id, kind, joined_at, created_at, updated_at)
SELECT gen_random_uuid()::text, p.id, p.member_id, 'GUARDIAN', COALESCE(p.created_at, now()), now(), now()
FROM profile p;

ALTER TABLE routine ADD COLUMN created_by VARCHAR(255) REFERENCES member (id);
UPDATE routine r SET created_by = (SELECT p.member_id FROM profile p WHERE p.id = r.profile_id);
-- NOT NULL 은 V23 에서 건다 — 아래 '되돌리기' 참고

-- 처음 만든 보호자가 나가도 프로필이 남을 수 있어야 한다 (4-3). 남은 보호자에게 넘기거나
-- 비워야 하는데, NOT NULL 이면 비울 수 없다.
ALTER TABLE profile ALTER COLUMN member_id DROP NOT NULL;

-- device_link.profile_id 는 운영에서 NULL 0건이지만 NOT NULL 도 V23 으로 미룬다 (같은 이유)
-- profile_invite 생성 (4-1)
```

- **새 코드는 `profile.member_id`를 읽지 않는다.** 다만 V23 전까지는 가입 때 **계속 채운다** —
  옛 서버로 되돌렸을 때 옛 코드가 이 값으로 프로필을 찾기 때문이다.
- 새 코드는 일과를 만들 때 `created_by`를 **항상** 채운다 (NULL 허용은 되돌리기 대비일 뿐이다).
- 검증: 운영 DB 사본에 먼저 돌려 행 수를 맞춘다 — 관계 73 = 프로필 73, 일과 67건 모두
  `created_by` 채움, `device_link.profile_id` NULL 0.

### 되돌리기 — V22 는 옛 서버가 그대로 돌 수 있어야 한다

Flyway 는 스키마를 되돌리지 않는다. 1단계 배포 뒤 문제가 생겨 **옛 서버 이미지로 되돌려도**
V22 스키마 위에서 옛 코드가 돌아야 한다. 그래서 V22 는 **추가만** 한다.

| V22 에서 NOT NULL 을 걸면 | 옛 서버에서 일어나는 일 |
|---|---|
| `routine.created_by` | 옛 코드는 이 컬럼을 모른다 → **일과 생성이 전부 실패** |
| `device_link.profile_id` | 옛 코드는 채우지만 확실히 하려고 미룬다 |
| `profile.member_id` DROP NOT NULL | 옛 코드는 이 값으로 프로필을 찾는다 → 새 코드가 계속 채우므로 문제없다 |

**옛 서버로 돌아가 있던 동안 생긴 행**은 관계·`created_by`가 비어 있다. V23 이 먼저 메운다.

### V23 — 메우고 줄인다 (다음 배포)

```sql
-- 되돌리기 동안 생긴 빈칸을 메운다
INSERT INTO profile_guardian (...) SELECT ... FROM profile p
 WHERE p.member_id IS NOT NULL
   AND NOT EXISTS (SELECT 1 FROM profile_guardian g WHERE g.profile_id = p.id);
UPDATE routine r SET created_by = (SELECT p.member_id FROM profile p WHERE p.id = r.profile_id)
 WHERE r.created_by IS NULL;
ALTER TABLE routine ALTER COLUMN created_by SET NOT NULL;      -- 채우지 못한 행이 있으면 여기서 멈춘다
ALTER TABLE device_link ALTER COLUMN profile_id SET NOT NULL;
DROP INDEX idx_profile_member;
ALTER TABLE profile DROP COLUMN member_id;
```

1단계 배포가 안정된 뒤(옛 경로를 읽는 곳 0, 되돌릴 일 없음을 확인) 연다.

## 6. API (1단계는 전부 하위 호환)

| 경로 | 변화 |
|---|---|
| 기존 전부 | `X-Profile-Id` 선택 헤더를 받는다. 없으면 기본 이룸이. 응답 모양 그대로 |
| `GET /api/member/me` | `profiles` 목록 필드 추가 |
| `POST /api/auth/logout` | 그 리프레시 토큰의 기기 세션만 끊는다 |
| `DELETE /api/member/me` | 4-3의 규칙으로 동작 (다른 보호자가 있는 이룸이는 남는다) |
| 🆕 `POST /api/profiles/{id}/invites` | 초대 코드 발급 (2단계) |

## 7-1. 엣지 케이스 — 경우마다 정한 동작과 확인 방법

"확인"은 무엇으로 증명하는지다. `서버 테스트` = 단위·통합 테스트, `운영 실측` = 배포 뒤
시험 계정으로 밟기, `사본` = 운영 DB 사본에서 마이그레이션.

### 초대

| # | 경우 | 동작 | 확인 |

| E1 | 코드를 만든 사람이 자기 코드를 넣는다 | 409 (이미 연결됨) | 서버 테스트 |
| E2 | 이미 연결된 사람이 넣는다 | 409 | 서버 테스트 |

## 8. 테스트 · 검증

- 권한 표(4-2)의 **칸마다** 허용 하나·거절 하나.
- 나가기 시나리오: 두 보호자 A·B가 한 이룸이에 붙음 → A 나가기 → A의 일과만 사라지고 B의 일과·별·이룸이는 남음 → B 나가기 → 이룸이·연결까지 사라짐.
- 탈퇴: A가 두 이룸이(하나는 혼자, 하나는 B와 공유)에 붙은 채 탈퇴 → 혼자인 이룸이는 삭제, 공유 이룸이는 B에게 남음.
- 로그아웃: A의 한 기기 로그아웃이 A의 다른 기기·이룸이 폰 세션을 끊지 않음.
- 이룸이 폰: 토큰의 `linkId`로 찾은 이룸이만 본다. 다른 이룸이를 헤더로 지정해도 403.
- 마이그레이션: 운영 DB 사본에서 V22 → 행 수 대조 → 기존 API 응답이 전후 같은지 스냅샷 비교.
- 배포 후 운영 실측: 기존 보호자 계정의 홈·일과·이룸이 폰이 그대로 동작하는지, 시험 계정 둘로 초대·나가기.
- **수정을 되돌리면 테스트가 실패하는지**까지 확인한다 (저장소 관례).

| 보호자 표시 이름 | `Member` 에는 아이디뿐이다. "만든 사람" 표시(E46)·함께하는 사람 목록에 보여줄 값이 없다 | #361 · #362 |

| 보호자 B 가 A 가 붙인 이룸이 폰을 끊을 수 있나 | 4-2(누구나)와 4-3(붙인 사람에게 묶임)을 함께 읽으면 모호하다 | #363 |
| 초대 화면에서 "코드"라는 말 | 09-18 합의의 `코드` 예외는 그 온보딩 시안에만 적용된다 | #362 |

**1단계가 함께 고치는 것** — 이룸이 폰 토큰의 주인이 보호자라서 지금은 **이룸이 폰에서 로그아웃해도 보호자 폰 세션까지 끊긴다**(`RefreshTokenService.revokeByToken`). 로그아웃을 기기 단위로 바꾸는 E33 이 이것도 막는다. 이룸이 폰이 자기 연결(`device_link`)을 끊는 서버 경로는 없으므로 #363 에서 만든다.

## 10. 작업 과정

단계마다 저장소 파이프라인을 그대로 탄다.

```
명세(이 문서) ─ 승인
   └ 단계별 이슈 등록 (/pro-github)
       └ 단계마다: worktree (/pro-init-worktree, origin/develop 기준)
            → 구현 (TDD — 권한 표·엣지 케이스 표의 번호를 테스트 이름에 단다)
            → 서버 테스트 · flutter test · analyze
            → 되돌려서 테스트가 실패하는지 확인
            → [1단계] 운영 DB 사본으로 V22 리허설 (행 수 대조 · 옛 서버로 되돌려 일과 생성)
            → 커밋 (/pro-commit) → develop push (사용자 승인)
            → 배포 (/pro-changelog-deploy, 사용자가 원할 때) → 운영 실측 (/pro-agent-test)
            → 완료 보고서 (/pro-report) — 엣지 케이스 표의 번호별 결과를 표로 남긴다
            → 라벨 작업완료
```

- **보고서에는 7-1 의 엣지 케이스 번호마다** "무엇으로 확인했나(테스트 이름 · 실측 캡처) · 결과"를
  적는다. 확인하지 못한 번호는 못 했다고, 왜 못 했는지와 함께 적는다.
- 1단계는 **스키마를 바꾸는 배포**다. 무중단 배포(#163)가 없어 배포 중 약 3분 502가 나고, 부팅에
  실패하면 되돌아갈 곳이 없다. 그래서 사본 리허설을 건너뛰지 않는다.
- V23 은 1단계가 안정된 것을 확인한 뒤 따로 연다.
