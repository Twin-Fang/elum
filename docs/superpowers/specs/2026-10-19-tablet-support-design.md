# 태블릿 정식 지원 설계 (iOS 아이패드 · Android 태블릿, 가로·세로)

작성: 2026-10-19 · 상태: **사용자 승인 (2026-10-19, 출시 방식·문구 결정 반영) → 구현 계획 작성 단계**
범위: `client/` (Flutter). 서버 변경 없음.

## 1. 왜 하는가

- 이룸을 쓰는 당사자(이룸이)와 교육 현장에서는 **휴대폰을 잘 쥐여 주지 않고, 태블릿이 없는 곳이 없다.**
  교육 프로그램도 대부분 태블릿으로 한다. 오늘 현장 실증에서 태블릿 지원 요구가 나왔다.
- 따라서 태블릿은 "나중에 호환되게" 가 아니라 **이룸이 화면의 주 기기**다.
  보호자는 휴대폰, 이룸이는 태블릿인 조합이 흔하다고 가정한다 (**가정** — 실증 수치는 없음).
- 지금은 iOS가 아이폰 전용(`TARGETED_DEVICE_FAMILY = "1"`)이고, 두 플랫폼 모두 세로 고정이며,
  레이아웃은 `ScreenUtil(designSize 393×852)` + Figma 절대 좌표라 큰 화면에서 폭만 3배 커지고
  높이는 그대로인 찌그러짐이 난다 (조사 결과는 §3).

## 2. 목표 · 비목표 · 반(反)목표

**목표**
1. 아이패드와 안드로이드 태블릿에서 **모든 기능이 가로·세로 모두 정상 동작**한다 (로그인 ~ 일과 ~ 보상 ~ 설정).
2. **애니메이션이 태블릿에서도 같은 의도로 보인다** (움직임 거리·속도·위치가 어긋나지 않는다).
3. 이룸이 화면은 태블릿에 맞게 **다시 구성**한다 (키운 카드, 가로 2단 등). 보호자 화면도 가로 2단을 쓴다.
4. 한 번 만든 규칙으로 **새 화면은 자동으로 같은 방식**을 따른다 (공통 지점 + 규칙 테스트).
5. 휴대폰 화면은 **한 픽셀도 달라지지 않는다** (회귀 0).

**비목표**
- 데스크톱·웹·폴더블 힌지 대응 (단, 창이 넓어져도 깨지지 않는 상한은 둔다)
- 다크 모드 (앱에 없음), Apple Pencil, 멀티 윈도우를 새로 활용하는 기능
- 서버·API 변경, 새 기능 추가
- 휴대폰의 가로 모드 (휴대폰은 계속 세로 고정)

**반목표 (이렇게 되면 기술적으로 동작해도 실패)**
- 태블릿에서 휴대폰 화면이 작게 떠 있는 것처럼 보이는 상태로 **B(적응형)를 영영 안 하고 끝나는 것**
- 화면마다 다른 breakpoint·다른 여백·다른 폭 상한이 생기는 것 (통일감 상실)
- 회전할 때 입력 중이던 글, 카드 페이저 위치, 진행 상태가 사라지는 것
- 이룸이 화면에서 에러·잘림이 보이는 것 (이룸이는 오류를 스스로 해석하지 못한다)

## 4. 핵심 결정과 이유

### 4.1 크기를 판단하는 단위: 기기 종류가 아니라 **창 크기 등급**
- `WindowSizeClass { compact, medium, expanded }` — **앱 창 폭** 기준 `<600 / 600~839 / ≥840` dp (Material 3 표준).
- 이유: 아이패드 분할 보기(1/3)나 안드로이드 분할 화면에서 태블릿이어도 창이 좁아진다. 기기 종류로 가르면 거기서 깨진다.
- 가로·세로는 `isLandscape`, 높이가 모자란 경우는 `isShortHeight`(창 높이 < 480dp)로 따로 본다.
- **기기 종류 판별(태블릿인가)** 은 방향 정책 한 곳에서만 쓴다. 화면 레이아웃과 문구는 쓰지 않는다.

### 4.2 크기 단위 `.w/.h` 처리: **창 하나에 배율 하나** (전역, 화면마다 다르지 않음)
`ScreenUtil`은 전역 싱글턴이라 화면별로 다른 배율을 줄 수 없다. 전환 중에는 두 화면이 동시에 떠 있으므로
화면별 배율은 깜빡임을 만든다. 그래서 **배율은 창 크기로만 정한다.**

```
compact (폰)          : 지금과 같다 (실제 창 크기 그대로) — 회귀 0
medium · expanded     : s = clamp(min(창폭/393, 창높이/852), 0.80, 1.30)
                        ScreenUtil에는 가상 크기 Size(393·s, 852·s)를 준다
                        → .w 와 .h 가 같은 s 라서 찌그러지지 않는다
```
- 가로 태블릿(높이 834 → s≈0.98)에서도 852 기준 절대 좌표 화면이 **높이 안에 들어온다.**
- 폭이 남는 만큼은 **레이아웃이 쓴다** (열을 늘리고 여백을 키운다). 부품 크기를 폭에 비례해 키우지 않는다.
- 높이가 `852×0.80`보다 모자라면(분할 화면 등) 그 화면은 **세로 스크롤로 폴백**한다 (잘리거나 CTA가 사라지지 않는다).
- **스파이크 1(구현 첫 작업)**: `ScreenUtil.configure(...)`로 창 크기 변경(회전·분할)마다 가상 크기를 갱신하는 것이
  실제로 되는지 확인한다. 안 되면 대안은 `.w` 확장을 자체 `Scale` 확장으로 치환하는 일괄 변환(417곳, 기계적)이다.
  결과에 따라 §6 일정이 바뀐다.

### 4.3 레이아웃 종류 3가지 (A와 B를 한 구조로)
모든 화면은 라우트 한 곳에서 **레이아웃 종류**를 선언한다 (`ScreenLayoutKind`). 선언이 없으면 기본값 `phoneColumn`.

| 종류 | 태블릿에서 | 용도 |
|---|---|---|
| `phoneColumn` (기본, **A**) | 폰 비율 열(폭 393·s)을 가운데 두고 양옆은 배경색 | 아직 적응형으로 안 만든 화면 — **새 화면도 자동으로 안전** |
| `contentColumn` | 폭 상한(§4.4)까지 늘린 가운데 열, 높이 부족 시 스크롤 | 폼·약관·설정류 |
| `adaptive` (**B**) | 전폭. 화면이 `compact` / `medium` / `expanded` 별 구성을 직접 가짐 | 이룸이 화면, 보호자 홈, 카드 확인 |

이렇게 하면 **A가 곧 B의 기본값**이다. B는 화면 단위로 `phoneColumn → adaptive`로 올리는 작은 변경이 된다.

### 4.4 레이아웃 토큰 (`AppLayout`, 간격·색처럼 한 곳)
화면에 숫자를 직접 쓰지 않는다 (코딩 규칙 §4). 값은 **초안**이며 실기기 확인 후 한 곳에서 조정한다.

| 토큰 | 값(dp, `.w` 적용 전) | 뜻 |
|---|---|---|
| `mediumMinWidth` / `expandedMinWidth` | 600 / 840 | 창 등급 경계 |
| `shortHeightMax` | 480 | 이 아래면 단일 열 스크롤 |
| `phoneColumnWidth` | 393 | A 열 폭 (× s) |
| `contentColumnMaxWidth` | 560 | 폼·설정 폭 상한 |
| `readingMaxWidth` | 640 | 약관 등 긴 글 |
| `masterPaneWidth` | 360 | 2단의 왼쪽(목록) 폭 |
| `paneGutter` | 24 | 2단 사이 간격 |
| `pageMargin` | compact 24 / medium 40 / expanded 56 | 좌우 여백 |
| `sheetMaxWidth` | 560 | 바텀시트 폭 상한 (가운데 정렬) |
| `dialogMaxWidth` | 420 | 다이얼로그 폭 상한 |
| `childCardMaxWidth` | 560 (세로) / 높이 기준 (가로) | 이룸이 카드 크기 상한 |
| `maxFrameScale` / `minFrameScale` | 1.30 / 0.80 | §4.2의 s 범위 |

### 4.5 방향 정책
| 기기 | 정책 | 방법 |
|---|---|---|
| 아이폰 | 세로만 (지금과 같음) | `UISupportedInterfaceOrientations` 유지 |
| 아이패드 | 4방향 | `UISupportedInterfaceOrientations~ipad` 추가, `TARGETED_DEVICE_FAMILY = "1,2"`, `UIRequiresFullScreen` 쓰지 않음 (분할 보기 허용 → 창 등급으로 흡수) |
| Android 폰 | 세로만 | 매니페스트를 `unspecified`로 풀고, Dart 시작 시 기기 짧은 변 < 600dp이면 세로 고정 (`OrientationPolicy` 한 곳) |
| Android 태블릿 | 전 방향 | 위 정책이 풀어 둠 |

### 4.6 시트·다이얼로그·토스트
`showElumSheet`·`showElumDialog`·토스트가 **폭 상한과 가운데 정렬을 한 곳에서** 처리한다 (화면 코드는 그대로).
태블릿 시트는 바닥에서 올라오되 `sheetMaxWidth`로 가운데 놓는다. 호출처 7곳은 수정하지 않는다.

### 4.7 애니메이션 원칙 (태블릿에서 같은 의도로 보이게)
- **시간(duration)·curve는 그대로** (`AppMotion`). 바뀌는 건 **거리·크기·속도**뿐이다.
- 거리는 "창 폭의 N%"가 아니라 **dp 토큰 × s**로 쓴다. 화면 전환 슬라이드는 폭의 25% → `pageSlideDistance`(dp) 한 값으로 바꾼다.
- 초당 속도(예: 카드 순서 변경 가장자리 자동 스크롤 360px/s)는 s를 곱한다.
- 위치가 절대 좌표인 연출(컨페티 발사 위치, 코치마크 구멍, 로그인 장면, 오로라 배경, 루미 모션, 별 보상)은
  **기준점을 위젯 자기 박스에서 계산**한다 (창 크기·고정 좌표 금지). 코치마크는 대상 위젯의 `RenderBox`로 구멍을 판다.
- 회전 중에도 애니메이션 컨트롤러 상태가 끊기지 않도록, 레이아웃이 바뀌어도 **같은 위젯이 같은 `Key`로 이어진다.**
- 배경 효과(오로라·컨페티)는 큰 화면에서 픽셀 수가 늘어 부하가 커진다. 저사양 태블릿 기준으로 확인하고,
  부하가 크면 렌더 해상도·입자 수를 등급별 토큰으로 낮춘다.

### 5.3 3순위 — 온보딩·로그인·연결·프로필
`login`, `role_select`, `consent*`, `splash`, `name`, `goals`, `character`, `image_style`, `pin`, `card_completion`,
`link_*`, `elumi_settings`, `guardians`, `invite_*`, `profile_switch`, `card_photo_permission`:
**contentColumn 또는 phoneColumn**. 로그인 장면(`login_scene`, `393.w` 고정)은 전폭 배경 + 가운데 일러스트로 재구성.
`phoneColumn`으로 시작해 폼 검증이 끝난 화면부터 `contentColumn`으로 올린다.

## 6. 구조 · 이름 (코딩 규칙 §4.2 형식)

**폴더**: `lib/core/layout/` 신설 (`core/`는 `features/`를 import하지 않는다 — 기존 규칙 유지).

| 새 이름 | 하는 일 | 이름만 보고 아는 것 |
|---|---|---|
| `WindowSizeClass` | compact / medium / expanded | 창 폭 등급 |
| `LayoutMetrics` | 등급·방향·`isShortHeight`·배율 s·안전영역을 한 번에 계산 | 지금 창의 레이아웃 정보 |
| `AdaptiveScope` | 루트에서 `LayoutMetrics`를 내려주고 `ScreenUtil` 가상 크기를 갱신 | 창 변화의 단일 반영 지점 |
| `AppLayout` (테마 확장) | §4.4 토큰, `context.layout` | 레이아웃 숫자 원본 |
| `ScreenLayoutKind` | phoneColumn / contentColumn / adaptive | 화면이 선언하는 종류 |
| `AdaptivePageFrame` | 종류에 맞춰 폭·정렬·배경·스크롤 폴백 | 라우트 래퍼 |
| `ContentColumn` | 가운데 폭 상한 열 | 폼용 |
| `TwoPaneLayout` | 목록+상세 2단, compact에서는 단일 열로 접힘 | 가로 2단 |
| `OrientationPolicy` | 기기별 방향 허용 | 방향 정책 한 곳 |
| `DeviceKind` | phone / tablet (물리 화면 짧은 변 ≥ 600dp) | 방향 정책용 기기 종류 |

- boolean은 `isLandscape`, `isShortHeight`, `isTabletDevice`, `hasTwoPanes`처럼 `is/has`로 쓴다.
- 라우트 래퍼는 `core/router`의 `slidePage`·`fadePage`에 끼운다 (전환 헬퍼가 이미 단일 지점).
- `context.layout`, `context.sizeClass`, `context.isLandscape` 확장을 `theme_context_ext.dart` 옆에 둔다.
- 기존 `ElumScaffold`·`RoutineFlowScaffold`의 `_frameHeight = 852` 같은 값은 s 배율 안에서 그대로 동작해야 한다 (§4.2).

## 9. 테스트 · 검증

**규칙 테스트 (우회 금지, 예외는 이유 있는 목록으로만)**
- `features/`에서 `MediaQuery.sizeOf(..).width` 비교, 숫자 breakpoint(`600`, `840`), `Platform.is*` 로 태블릿 판별 금지 → `context.sizeClass`만
- `1.sw` · `1.sh` · `ScreenUtil()` 직접 호출 금지 (현재 1곳 `home_coach_mark.dart:64`은 이전)
- `showModalBottomSheet(` · `showDialog(` 직접 호출 금지 (공통 헬퍼만)
- 슬라이드 거리·속도에 창 폭 비례 값 금지, `AppLayout`·`AppMotion` 토큰만
- `adaptive` 선언 화면은 태블릿 매트릭스 테스트 목록에 반드시 포함

**매트릭스 테스트** (`device_sizes_test.dart` 확장, `devicePixelRatio`를 반드시 고정 — 기존 함정): 모든 화면 ×

| 크기 | 설명 |
|---|---|
| 393×852 | 아이폰 (회귀 기준) |
| 744×1133 / 1133×744 | 아이패드 미니 |
| 820×1180 / 1180×820 | 아이패드 10.9~11" |
| 1024×1366 / 1366×1024 | 아이패드 13" |
| 800×1280 / 1280×800 | 안드로이드 10" |

**동작 테스트**: 회전해도 입력 글·페이저 위치 유지, 시트 폭 상한, 컨페티·코치마크 위치가 대상 위젯 박스 안, 전환 슬라이드 거리.

- `/pro-launch`로 구동·캡처 (raw adb 좌표 조작 금지).

## 10. 단계 (각 단계는 별도 이슈, 앞 단계가 끝나야 다음)

| 단계 | 내용 | 끝났다는 기준 |
|---|---|---|
| **P0 스파이크** | §4.2 가상 크기 방식이 회전·분할에서 되는지 확인 (버릴 코드) | 되면 진행, 안 되면 `Scale` 치환안으로 설계 갱신 후 재승인 |
| **P1 기반 + A** | `core/layout`, 토큰, `AdaptivePageFrame`, 시트·다이얼로그·토스트 폭, 방향 정책, 네이티브 설정, 규칙·매트릭스 테스트 | 모든 화면이 태블릿에서 깨지지 않음 (phoneColumn), 폰 골든 변화 0 |
| **P2 이룸이 B** | §5.1 + 애니메이션 보정 (컨페티·루미·별·페이저·전환) | 이룸이 흐름 전체가 태블릿 가로·세로에서 실기 확인 |
| **P3 보호자 B** | §5.2 | 보호자 흐름 전체 실기 확인 |
| **P4 나머지** | §5.3, 문구(§8), 광고, 공유 | 화면 매트릭스 표 전부 확인됨 |
| **P5 출시 자산** | 스토어 아이패드 스크린샷(13"·12.9"), 안드로이드 태블릿 스크린샷(7"·10"), 심사 노트 갱신 | 제출 가능 |

**출시 방식 (결정됨, 2026-10-19)**: **전부 맞춘 뒤 안드로이드·아이패드를 함께 출시한다.** 단계별 중간 출시는 없다.
- P1~P5는 `develop`에 쌓되, 사용자에게 열리는 두 스위치는 **마지막에 한꺼번에** 켠다:
  Android 방향 해제(`OrientationPolicy`) · iOS `TARGETED_DEVICE_FAMILY = "1,2"`와 아이패드 방향 키.
  그 전까지 두 값은 지금(폰 세로 고정, 아이폰 전용) 그대로라 **사용자에게 보이는 변화가 없다.**
- 켜기 전 조건: §9 매트릭스·실기 확인이 전 화면 통과, P5 스토어 자산 준비 완료.
- 단, 이미 Android 16+ 대화면에는 세로 고정이 풀려 노출되어 있다 (`targetSdk` 확인은 P1 첫 작업).
  출시 전에 이 노출이 문제가 되면 별도 핫픽스 이슈로 다룬다.

## 11. 결정 사항과 남은 확인

**결정됨 (2026-10-19, 사용자)**
- 출시: 전부 맞춘 뒤 안드로이드·아이패드 **함께** 출시 (§10). 중간 출시 없음.
- 문구: "휴대폰" → **"기기"로 통일** (§8).
- 이룸이 화면(P2): 디자이너 시안을 기다리지 않고 §5.1 제안안으로 먼저 만든다. 출시 전에 디자이너 확인을 받고, 시안이 다르면 고친다.

**남은 확인 (진행을 막지 않음)**
1. **현장 태블릿 기종**: 알려 주시면 매트릭스에 그 해상도를 추가한다. 없으면 §9 표대로 간다.
2. **디자이너 확인 시점**: 출시 전 어느 단계에서 받을지 (P2 완료 직후 권장).

### 제 결정 (검토자 질문에 대한 제 판단 — 틀리면 알려 주세요)
- **P0 스파이크 실패 시**: 자체 `Scale` 치환(기계적 일괄 변환)을 **미리 승인된 대안**으로 둔다. 다만 일정·범위가 바뀌므로 결과를 근거와 함께 보고한다.
- **`ElumScaffold`·`RoutineFlowScaffold` 구조 변경**: 폰 출력이 같다는 조건에서 P1 안에서 고쳐도 된다. 같지 않으면 고치지 않고 보고한다.
- **폰 회귀 0의 기준**: 기존 골든이 변하지 않을 것 + 골든이 없는 화면은 **P2·P3에서 건드리기 전에** 폰 골든을 먼저 만든다. compact 경로는 `ScreenUtil`에 실제 창 크기를 그대로 주므로 구조상 동일하다.
- **태블릿 판별 경계**: 짧은 변 ≥ 600dp면 태블릿으로 본다. 펼친 폴더블·큰 표시 크기 설정 폰도 포함되며 그대로 받아들인다.

- 화면별 임의 breakpoint·임의 폭 상한
