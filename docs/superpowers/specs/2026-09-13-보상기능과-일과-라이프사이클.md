# A. 서버 변경

## A-1. `Routine` 엔티티 — 보상 필드 추가 🔴

```java
/// 보호자가 정한 보상(강화물). 없으면 null — 건너뛰기를 허용한다.
/// 앱이 보상을 주지 않는다. 아이에게 보여주고 상기시키는 용도다.
@Column(length = 100)
private String rewardText;

/// 프리셋에서 고른 경우 그 키. 직접 입력이면 null.
/// 아동 화면에 그림을 띄우려면 키가 필요하다 — 자유 텍스트는 글자만 나온다.
@Column(length = 30)
private String rewardPresetKey;
```

**마이그레이션** `V9__add_reward_to_routine.sql`

```sql
ALTER TABLE routine ADD COLUMN reward_text VARCHAR(100);
ALTER TABLE routine ADD COLUMN reward_preset_key VARCHAR(30);
```

## A-2. 보상 프리셋 상수 🔴

| key | 라벨 | 이모지 |
| --- | --- | --- |
| `SNACK` | 좋아하는 간식 | 🍪 |
| `VIDEO` | 유튜브 10분 | 📺 |
| `PLAY` | 좋아하는 놀이 | 🧸 |
| `WALK` | 산책 | 🚶 |
| `CUSTOM` | 직접 입력 | ✏️ |

> 프리셋을 두는 이유는 **아동 화면에 그림을 띄우기 위해서**다.
> 자유 텍스트만 받으면 글자를 못 읽는 사용자에게 아무 의미가 없다.

## A-3. API 변경 🔴

| API | 변경 |
| --- | --- |
| `POST /api/routines` | 요청에 `rewardText`, `rewardPresetKey` 추가 (**선택**, null 허용) |
| `PATCH /api/routines/{id}/reward` | 🆕 보상만 수정 |
| `GET /api/routines/{id}` · `/today` | 응답에 `rewardText`, `rewardPresetKey` 포함 |
| `GET /api/routines/recent-rewards` | 🆕 최근 사용한 보상 **최대 3개** (중복 제거, 최신순) |
| `POST /api/routines/{id}/duplicate` | 🆕 같은 steps로 **오늘** 일과 생성 (**AI 호출 없음** · 날짜 파라미터 없음) |
| `DELETE /api/routines/{id}` | 🆕 **임시저장(`PENDING_REVIEW`) 일과만 삭제**. 그 외 상태는 409 |

### `duplicate` 동작 규칙

```
원본의 title · steps(title/description/ttsText/imagePath) · reward를 복사
→ 새 Routine 생성 (status = CONFIRMED, scheduledAt = 오늘 09:00 고정)
→ steps의 completed는 전부 false로 초기화
→ rawInputText/sanitizedInputText는 복사하지 않는다 (원문 미보관 원칙)
```

## A-4. 목록 조회 🔴

현재 보호자 홈이 `findAllByMemberId`로 **전부** 가져온다. 세 구간으로 나눈다.

```java
// 오늘    : status ∈ {CONFIRMED, COMPLETED} AND scheduledAt ∈ [오늘 00:00, 23:59:59] (KST)
// 준비 중  : status = PENDING_REVIEW  (승인 대기 · 아이에게 보이지 않음)
// 지난     : scheduledAt < 오늘 00:00  → 최신순 10개만
```

**`confirm()` 변경** — 승인 시 `scheduledAt`을 그날로 갱신한다.

```java
routine.setStatus(RoutineStatus.CONFIRMED);
routine.setScheduledAt(LocalDate.now().atTime(9, 0));
```

> **지난 일과를 삭제하지 않는다.** 수행률 추이(P1)의 원본 데이터이고,
> 보호자가 "이 날은 왜 안 했지"를 확인하는 근거다.

# B. 화면 명세

## B-1. 보호자 홈 `guardian_home_screen` — **수정** 🔴

### 현재
```
[헤더]
[새로운 일과 만들기 카드]
[오늘 일과]        ← 있음
[추천 일과]
```

### 변경 후
```
[헤더]
[새로운 일과 만들기 카드]

오늘                                    ← CONFIRMED/COMPLETED · scheduledAt 오늘
  ┌──────────────────────────────┐
  │ ☂️ 비 오는 날 학교 가기         │
  │ ●●●○○  3/5                   │
  │ 🍪 다 하면: 젤리 먹기          │  ← 보상 있을 때만
  └──────────────────────────────┘

준비 중                                  ← PENDING_REVIEW (승인 대기)
  ┌──────────────────────────────┐      있을 때만 표시
  │ 🏥 병원 가기                   │
  │ 아직 아이에게 보이지 않아요      │
  │                    [ 확인하기 ] │  → 카드 검토 화면
  └──────────────────────────────┘

지난 일과  ▾ (기본 접힘)                  ← scheduledAt이 오늘 이전
  ┌──────────────────────────────┐
  │ 🎒 아침 등교 준비   5/5         │
  │                   [ 다시 하기 ]│
  └──────────────────────────────┘

추천 일과                                ← 기존 유지
```

### 섹션 규칙

| 섹션 | 조건 | 표시 |
| --- | --- | --- |
| `오늘` | status ∈ {CONFIRMED, COMPLETED} AND scheduledAt = 오늘 | 항상. 0건이면 "오늘은 등록된 일과가 없어요" |
| `지난 일과` | scheduledAt < 오늘 00:00 | 1건 이상일 때만 · 기본 접힘 · 최근 10개 |

**임시저장(`PENDING_REVIEW`)은 섹션을 따로 두지 않고 `오늘` 안에 배지로 표시한다.**

```
오늘
 ┌──────────────────────────────┐
 │ ☂️ 비 오는 날 학교 가기         │
 │ ●●●○○  3/5                   │
 │ 🍪 다 하면: 젤리 먹기           │
 └──────────────────────────────┘
 ┌──────────────────────────────┐
 │ 🏥 병원 가기        [ 임시저장 ]│  ← 배지
 │ 이어서 수정할 수 있어요          │
 └──────────────────────────────┘
      탭 → 카드 검토 화면으로 바로 이동
```

> **`PENDING_REVIEW`는 "승인 대기"가 아니라 "임시저장"이다.**
> 보호자 입장에서는 *만들다 만 일과*이고, 이어서 수정할 수 있다는 게 핵심이다.
> 화면 문구·배지에 "승인"이라는 말을 쓰지 않는다.

### 타일 공통 요소

| 요소 | 조건 |
| --- | --- |
| 보상 줄 | `rewardText != null` 일 때만 |
| 진행률 `3/5` | steps 중 completed 개수 |
| **[다시 하기]** | **지난 일과 타일에만** |
| **[임시저장] 배지** | `status = PENDING_REVIEW` 일 때만. 타일 전체가 탭 대상 → 카드 검토 화면 |

### [다시 하기] 동작

```
탭 → duplicate API 즉시 호출 (확인 시트 없음 · 날짜 묻지 않음 · AI 호출 없음)
   → 오늘 일과로 생성 (status = CONFIRMED, scheduledAt = 오늘 09:00)
   → 성공: 오늘 섹션 상단에 추가 + 토스트 "오늘 일과로 만들었어요"
   → 실패: 토스트 + 에러 코드 노출 (E-xxxx). 원본은 그대로
```

> **탭 한 번으로 끝나야 재사용 가치가 있다.** "다시 하기"의 의도가 곧 "지금 또 할래"다.
> 내일 것으로 만들고 싶으면 내일 다시 누르면 된다.

> 별도 "저장된 일과" 개념을 만들지 않는다. **지난 일과가 곧 저장소**다.

### 날짜 UI를 만들지 않는다 (2026-09-13 회의 결정)

캘린더·날짜 피커·요일 계산을 전부 만들지 않는다. 대신 **승인 시점이 곧 그 일과를 하는 날**이 된다.

```java
// RoutineService.confirm()
routine.setStatus(RoutineStatus.CONFIRMED);
routine.setScheduledAt(LocalDate.now().atTime(9, 0));   // ← 승인한 날로 갱신
```

### 이 한 줄이 만드는 것

| 사용 패턴 | 동작 |
| --- | --- |
| 오늘 할 일 | 만들고 **바로 승인** → 아이 화면에 뜸 |
| **내일 병원** | 오늘 미리 만들고 **임시저장** → 내일 홈에서 열어 `아이 화면으로 시작하기` → 그때 아이 화면에 뜸 |
| 재사용 | `지난 일과`에서 [다시 하기] → 오늘 일과로 즉시 생성 |

> 아동 `GET /api/routines/today`는 **`PENDING_REVIEW`를 제외**한다(기존 구현).
> 승인 전 일과는 아이에게 보이지 않으므로, **승인이 곧 "오늘 할 일로 올리기"** 다.
> 날짜를 고르는 UI 없이 미리 만들어두기가 성립한다.

### B-4a. 검토 화면 이탈 팝업 — **신규** 🔴

**현재 문제** — `card_review_screen`의 뒤로가기가 `context.pop()`으로 **아무 경고 없이 나간다.**
AI 호출까지 마친 카드가 화면에서 사라지고, 보호자는 일과가 만들어졌는지도 모른 채 홈으로 돌아온다.

### 팝업

```
┌──────────────────────────────────┐
│  아직 아이에게 보내지 않았어요      │
│                                  │
│  임시저장하면 나중에 이어서        │
│  수정할 수 있어요.                │
│                                  │
│  [ 삭제하기 ]      [ 임시저장 ]   │
│                                  │
│       계속 편집하기                │
└──────────────────────────────────┘
```

| 버튼 | 동작 |
| --- | --- |
| **임시저장** | 그대로 두고 홈으로. 홈 `오늘` 섹션에 `[임시저장]` 배지로 노출 |
| **삭제하기** | `DELETE /api/routines/{id}` → 홈으로. **한 번 더 묻지 않는다** (이미 이 팝업이 확인 단계다) |
| 계속 편집하기 | 팝업만 닫는다 (기본 동작) |

### 발동 조건

| 경로 | 팝업 |
| --- | --- |
| 상단 뒤로가기(`onBack`) | **뜬다** |
| 안드로이드 시스템 뒤로가기 | **뜬다** (`PopScope`) |
| `아이 화면으로 시작하기` | 안 뜬다 (정상 승인 경로) |
| 이미 `CONFIRMED`인 일과를 다시 열었을 때 | **안 뜬다** — 임시저장 상태가 아니다 |

> ⚠️ **AI 호출은 한 번이 곧 비용이다**(`routine_notifier.dart` 주석).
> 경고 없이 이탈해 같은 일과를 다시 만들면 비용이 두 번 나간다.
> 이 팝업은 UX 문제이자 비용 문제다.

> ⚠️ **이게 자문의 핵심 요구다.** *"수행하는 동안 최종 보상을 계속 확인할 수 있어야 한다."*
> 완료 후에만 보여주면 기존 별 보상과 다를 게 없다.

# F. 설계 판단 근거 — "왜 이렇게 했는가"

> 기능을 **넣은 이유보다 빼기로 한 이유**를 남긴다.
> 중간심사 질의응답, 개발노트의 「제안서 대비 변경사항 및 사유」, 실증보고서에 그대로 쓰인다.
> 나중에 "왜 없나요?"를 들었을 때 **그때 이렇게 판단했다**고 답할 수 있어야 한다.

## F-1. 왜 캘린더·날짜 선택이 없는가

**발달장애인의 일과는 "오늘 뭐 하지"가 본질이다.**

먼 미래의 일정을 관리하는 것은 일반 캘린더 앱의 몫이고, 이 서비스가 푸는 문제가 아니다.
보호자가 필요로 하는 것은 *"내일 뭐 있더라"* 가 아니라 *"지금 이걸 어떤 순서로 시키지"* 다.

- 애초에 `07-mvp-scope.md` 제외 목록에 **"일정 캘린더 — 핵심 생성 흐름과 무관"** 으로 처음부터 있었다.
- 자문에서도 *"MVP는 최대한 가볍게, 기능을 계속 추가하면 원래 목적이 흐려진다"* 는 지적을 받았다.
- 날짜 피커를 넣으면 요일 계산·날짜 표기·타일 배지·정렬 규칙이 따라붙는다. 보호자가 얻는 것에 비해 화면이 무거워진다.

**대신 승인 시점을 날짜로 삼는다.** 미리 만들어 두고 그날 승인하면 된다.
이 방식은 UI를 하나도 늘리지 않으면서 "내일 병원"을 커버한다.

## F-2. 왜 반복 일과(매일/매주)가 없는가

반복은 **자동 생성 스케줄러 · 중복 방지 · 템플릿 수정 시 과거 인스턴스 처리 · 예외 날짜(공휴일·아픈 날)** 가
한 묶음으로 딸려온다. 하나만 만들면 나머지가 반드시 문제를 일으킨다.

**[다시 하기]가 반복의 실사용 대부분을 대체한다.** 어제 한 일과를 탭 한 번으로 오늘 것으로 만든다.
보호자가 "오늘은 안 해도 되는 날"을 스스로 판단할 수 있다는 점에서 오히려 통제권이 보호자에게 남는다.

## F-3. 왜 아이 화면에 오늘 것만 보이는가

**아이에게 목록을 주면 "무엇을 고를까"가 또 하나의 과제가 된다.**

자문에서 확인한 원칙이 *"한 카드에 하나의 행동"* 이었다. 이 원칙은 카드 내용뿐 아니라
**화면 구조에도 적용**되어야 한다고 판단했다. 그래서 미완료 중 가장 이른 하나만 크게 보여준다.

> 반대 논리도 검토했다 — 전년도 수상작 토닥이는 주간 시간표를 제공했고,
> 근거는 *"예측 가능한 하루가 안정을 준다"* 였다.
> 우리는 **"오늘 안에서의 예측 가능성"** 을 먼저 확보하기로 했다.
> 내일 예고는 오늘을 다 마쳤을 때 한 줄로 붙이는 방안을 본선 범위로 남겨 둔다.

## F-4. 왜 보상을 필수로 하지 않는가

**보호자 입력 부담이 이 서비스의 최대 이탈 요인**이기 때문이다.

- 자문: *"발달장애인 보호자는 이미 돌봄·이동·교육 부담이 크다. 설정까지 복잡하면 실사용성이 떨어진다."*
- 전년도 수상팀도 실증에서 같은 피드백을 받았다 — *"보호자가 서술형으로 길게 작성해야 하므로 부담이 크다."*

보상이 없으면 보상 UI 전체를 숨기고 기존 별 보상만 동작한다. **없어도 서비스가 성립한다.**

## F-5. 왜 온보딩에서 더 묻지 않는가 (집/학교/직장 등)

**개별화를 설정이 아니라 편집으로 하기로 했다.**

물어서 맞추려면 문항이 계속 늘어나고, 답이 바뀌면 설정으로 다시 들어가야 한다.
그런데 자문의 핵심은 *"AI 결과는 정답이 아니라 초안이고, 보호자의 추가·삭제·수정이 핵심"* 이었다.

```
설정으로 개별화                 편집으로 개별화 (채택)
───────────────                ──────────────────
온보딩 문항 증가               온보딩 4단계 유지
→ 보호자 이탈                  → AI가 초안 생성
→ 그래도 안 맞음                → 보호자가 지우고 고침 = 개인화
                              → 최근 보상·지난 일과가 쌓이며 맞춰짐
```

## F-6. 왜 앱이 보상을 "지급"하지 않는가

**앱은 약속을 기억하고 보여줄 뿐, 주는 사람은 보호자다.**

자문에서 확인한 역할 경계다 — *"앱이 보상을 결정하는 것이 아니라 보호자가 설정한다"*,
*"앱만으로 자립이 만들어지는 것이 아니라 오프라인에서 구성된 구조를 보조한다."*

그래서 보상 완료 화면에 "받았어요" 같은 지급 버튼을 두지 않는다.
보호자에게 완료를 알리는 기능(P1)도 **앱이 처리를 끝내는 것이 아니라 보호자에게 넘기는** 형태다.

## F-7. 왜 지난 일과를 지우지 않는가

수행률 추이(P1)의 **원본 데이터**이고, 보호자가 *"이 날은 왜 못 했지"* 를 확인하는 근거다.
자문의 리포트 예시가 정확히 이 데이터를 요구한다 — 평소 100%이던 수행률이 30%로 떨어진 날을 찾는 용도다.

대신 기본 접힘 + 최근 10개로 **보이지 않게** 한다. 지우는 것과 접는 것은 다르다.

> 과제분석·연쇄 구조에 맞다고 판단했다.

## H-2. 문제 ⚠️

### ① 이름만 알면 남의 계정에 들어간다

```
보호자 A가 "하늘이"로 가입
   → 다른 사람이 온보딩에서 "하늘이" 입력
   → 같은 계정에 로그인됨 (일과·카드·아이 기록 전부 열람)
```

**실증(10월)에서 참여자 호칭이 겹치면 서로의 데이터가 섞인다.**
동의를 받고 진행하는 실증에서 이런 일이 생기면 실증 자체가 무효가 될 수 있다.
개인정보 최소 수집을 내세우는 서비스에서 더 치명적이다.

> 🔴 **실증 전에 반드시 해결해야 한다.** 중간심사(9/18)까지는 데모 환경이라 위험이 낮지만,
> 실제 사용자에게 설치하는 순간부터는 다른 문제다.

### ② 보호자가 다른 기기에서 진행 상황을 보면 최신이 아닐 수 있다

진행 상황이 **로컬 우선**이다. 아이 기기에서 3/5를 했어도 서버 반영이 지연되면
보호자 기기에서는 이전 값이 보인다.

- 오프라인 퍼스트는 아이 화면이 네트워크에 흔들리지 않게 하려는 의도된 설계였다(이슈 #140)
- 그런데 **보호자 원격 확인**이 들어오면 "기기가 진실"과 "서버가 진실"이 충돌한다

| 안 | 내용 | 비용 |

> 온보딩 화면을 하나도 늘리지 않고 계정이 분리된다.

## H-5. 보호자 원격 확인 (본선 범위)

```
아이 기기                     서버                      보호자 기기
  카드 완료 → 즉시 로컬 반영
           → 백그라운드 동기화  →  최신 진행률 저장
                                              → 보호자가 열면 서버 값 조회
                                                "하늘이가 3/5 했어요"
```

| 규칙 | 내용 |
| --- | --- |
| 아이 화면 | **로컬 우선 유지** — 네트워크 때문에 아이 화면이 멈추면 안 된다 |
| 보호자 화면 | **서버 값 조회** — 원격 확인이 목적이므로 서버가 진실 |
| 표시 | 마지막 동기화 시각을 함께 보여준다 ("방금 전", "5분 전") |

> 두 화면이 서로 다른 진실을 봐도 된다. **목적이 다르기 때문이다** —
> 아이 화면은 *지금 수행*, 보호자 화면은 *확인*이다.
> 다만 보호자 화면에는 **언제 기준인지**를 반드시 표시해 혼란을 막는다.
