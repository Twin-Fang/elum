# 1. 근본 문제 — **보호자라는 주체가 없다**

소장님 자문의 핵심은 **"보호자가 설정하고 관리한다"** 였다.
그런데 현재 데이터 구조에는 **보호자 계정이 존재하지 않는다.**

```java
// Member.java — 한 덩어리다
username      // ← 아이 이름이 곧 로그인 ID
password      // ← 클라가 모든 계정에 fixedPassword를 보낸다
nickname      // 아이 호칭
character     // 아이가 고른 캐릭터
supportGoals  // 도움 목표
totalStars    // 아이가 모은 별
```

**한 `Member` = 아이 1명 + 보호자 1명이 뭉쳐 있다.** 그래서:

- 보호자가 **여러 아이**를 관리할 수 없다
- 보호자와 아이가 **다른 기기**를 쓰는 구조가 성립하지 않는다
- "보호자가 관리한다"가 **PIN으로 화면을 가리는 것** 이상이 되지 못한다

## 필요한 구조

```
현재                          필요
────                          ────
Member (아이 이름 = ID)        보호자 계정 (아이디/비밀번호)
  └ 일과                        ├ 아이 프로필 A ─ 일과
                                └ 아이 프로필 B ─ 일과
```

> 이 분리가 **자문의 "보호자가 관리한다"를 구조로 옮기는 일**이다.
> 화면을 추가하는 문제가 아니라 데이터 모델을 바꾸는 문제다.

# 2. 진단 — 데모에 최적화된 지점들

| # | 항목 | 현재 상태 | 실사용에서의 위험 |
| --- | --- | --- | --- |
| 1 | **인증** | `signInWithName(name)` + **`fixedPassword`** (모든 계정 동일) | **아이 호칭만 알면 남의 계정에 로그인된다.** 실증 참여자 호칭이 겹치면 데이터가 섞인다 |
| 2 | **계정 구조** | `Member` = 아이. 보호자 계정 없음 | 다자녀 불가 · 기기 분리 불가 · 보호자 권한 개념 없음 |
| 3 | **PIN** | 미설정이면 **그냥 통과** (`mode_switch_screen.dart:55`) | 온보딩을 건너뛴 상태에서 아이가 보호자 모드에 들어간다 |
| 4 | **mock 스위치** | `useMock` 기본값 **`true`** (`app_config.dart:64`) | 환경변수로 끄지 않으면 서버를 안 탄다. 배포 설정에 의존 |
| 5 | **카드 fallback** | `1차 서버 → 2차 기본 세트 → 3차 하드코딩 데모 카드` | AI 실패 시 **하드코딩 카드가 AI 결과처럼 보인다.** 실증 데이터가 오염된다 |
| 6 | **진행 상황** | "기기가 진실" — 로컬이 서버를 덮는다 | 보호자가 다른 기기에서 보면 최신이 아니다 |
| 7 | **개발자 도구** | `showDevTools` 기본 false지만 릴리스에서도 켤 수 있음 | 의도된 설계(심사자 확인용). 정식 출시 전 차단 필요 (이슈 #13) |
| 8 | **다자녀** | 없음 | 형제자매가 있는 가정을 커버 못 함 |

> **4·5번은 데모를 끝까지 성립시키려는 의도된 안전장치였다**
> (서비스 원칙 6번 — *"어떤 실패 상황에서도 데모는 끝까지 진행되어야 한다"*).
> 데모에서는 옳았지만, **실증에서는 정반대로 작동한다** — 실패를 숨기면 그 실패를 발견할 수 없다.

## 🟠 실증 전 (10월 초) — **여기가 마지노선**

실제 사용자에게 앱을 설치하는 순간부터는 다른 문제다.

| # | 할 일 | 이유 |
| --- | --- | --- |
| 1 | **계정 분리** — `signIn(name, pin)` | 이미 받는 `guardianPin`을 자격에 포함. 같은 호칭이어도 PIN이 다르면 다른 계정. **온보딩 화면을 늘리지 않는다** |
| 2 | **PIN 미설정 통과 제거** | 개발 편의 코드가 실사용에 남아 있으면 안 된다 |
| 3 | **mock 기본값 `false`로** | 실증 빌드가 mock으로 도는 사고를 막는다 |
| 4 | **fallback 카드 표시** | 하드코딩 카드가 나왔을 때 보호자가 알 수 있게. 실증 데이터에서 제외할 수 있어야 한다 |
| 5 | 실증 빌드 점검 체크리스트 | 위 4개 + devTools off 확인 |

## 🟡 본선 이후 — 구조 개편

| # | 할 일 |
| --- | --- |
| 1 | **보호자 계정 ↔ 아이 프로필 분리** (데이터 모델 변경 + 마이그레이션) |
| 2 | 정식 회원가입 (아이디/비밀번호 또는 소셜) |
| 3 | **다자녀 지원** |
| 4 | 보호자·아이 **기기 역할 구분** + 원격 진행 확인 |
| 5 | 보호자 완료 알림 |

# 4. 실증 빌드 체크리스트 (10월)

> 실증 직전에 이 표를 그대로 확인한다. 하나라도 어긋나면 실증 데이터를 신뢰할 수 없다.

| 확인 | 기준값 |
| --- | --- |
| ☐ `ELUM_USE_MOCK` | **false** |
| ☐ `ELUM_SHOW_DEV_TOOLS` | **false** |
| ☐ `ELUM_ENABLE_NETWORK_LOG` | false (릴리스에서 자동 차단) |
| ☐ 계정 | 참여자별로 **분리 확인** (같은 호칭 2명 테스트) |
| ☐ PIN | 미설정 통과 경로 제거 확인 |
| ☐ 카드 생성 | 서버 정상 응답 확인 (fallback으로 도는지 로그 확인) |
| ☐ 프롬프트 | 운영 DB에 최신 프롬프트 반영 확인 (관리자 페이지) |
| ☐ 서버 | `api.elum.chuseok22.com` 헬스체크 |

# 5. 발표에서 어떻게 말할 것인가

이 진단은 **약점이 아니라 로드맵**이다. 심사에서 "실사용 가능한가"를 물으면 이렇게 답한다.

> "현재 버전은 핵심 흐름을 검증하는 데 집중했습니다.
> 실증을 앞두고 계정 분리와 안전장치를 먼저 정리하고 있고,
> 보호자 계정과 아이 프로필을 분리하는 구조 개편을 다음 단계로 잡고 있습니다.
> 자문에서 확인한 **'보호자가 관리한다'** 는 원칙을 화면이 아니라 **데이터 구조에서** 만들려는 것입니다."

> ⚠️ **먼저 말하지는 않는다.** 묻지 않은 한계를 스스로 꺼낼 필요는 없다.
> 다만 질문을 받았을 때 **"알고 있고 계획이 있다"** 는 답이 준비되어 있어야 한다.
