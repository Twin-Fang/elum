# 공동 보호자 일과 완료 상태 정합성 (#561)

## 요구와 확인 근거

같은 이룸이의 두 일과를 완료하면 생성자와 조회 휴대폰에 관계없이 보호자 홈 및 이룸이 홈에서 모두 완료 상태를 표시해야 한다.

2026-10-05 13:07 운영 로그에서 완료 집합 PUT 요청은 모두 200으로 처리됐고, 두 일과의 마지막 요청에는 각각 카드 5개와 4개가 포함됐다. 두 보호자의 생성·확정 요청은 같은 프로필을 지정했다. 로그에는 조회 응답 본문이 없어 실제 응답 완료 상태와 이름까지 확정할 수는 없다.

최신 develop의 두 목록 provider는 만들기 흐름에 남은 일과를 먼저 넣고 같은 ID의 서버 일과를 제외한다. 완료된 서버 일과를 주어도 옛 CONFIRMED 상태가 표시되는 회귀 테스트로 코드 결함을 재현했다. 사용자 제보의 생성자별 방향까지 단일 원인으로 확정한 것은 아니다.

## 승인한 수정 설계

- 같은 ID가 조회 목록에 있으면 조회된 최신 일과를 사용하고 서버 순서를 유지한다.
- 조회 목록에 아직 없는 새 일과는 기존과 같이 즉시 표시한다.
- 보호자 홈과 전환한 이룸이 홈 모두 같은 우선순위를 적용한다.
- 진행률 계산 및 미전송 오프라인 체크 대기열은 변경하지 않는다.
- 기존 임시저장, 빈 카드, 날짜 필터는 유지한다.

## 정상 및 실패 경로

- 정상 조회: 두 보호자와 이룸이 화면 모두 서버의 완료 일과를 표시한다.
- 생성 직후 조회 전: 만들기 흐름의 새 일과를 표시해 공백을 방지한다.
- 조회 중 및 통신 실패: 기존 provider의 직전 목록과 저장소 캐시 정책을 유지한다.
- 미전송 체크: 해당 일과의 로컬 체크를 계속 표시해 완료/해제 조작을 잃지 않는다.
- 임시저장 옛 상태가 남은 경우: 서버의 같은 ID 승인 일과를 배제하지 않는다.

## 검증과 남는 범위

두 보호자의 서로 다른 생성 일과, 서버 완료 일과 우선, 새 일과 즉시 노출, 미전송 체크 보존, 임시저장 상태 잔존을 회귀 테스트한다. 보호자 홈 및 진행률 관련 기존 테스트와 정적 분석을 실행한다.

실제 세 휴대폰의 화면 비교는 새 빌드 배포 후 필요하다. 이 수정은 앱 표시 병합에 한정되며 #562의 이름 조회와 서버 동시 쓰기 정합성은 별도로 추적한다.
