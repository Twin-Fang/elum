# 알림(종 아이콘, 알림·공지 화면, 푸시) 설계

상태: 화면은 사용자와 시안으로 합의 (2026-10-19). 동작 방식은 "일반 공개 앱이 쓰는 표준 방식으로" 위임받아 정함 (2026-10-19).
구현 이슈: 클라 화면 #826, 서버 #827, 클라 푸시 수신 #828. 상위 이슈 #699.

## 목적과 이유
보호자가 앱을 열기 전에는 이룸이의 일과 완료, 다른 보호자의 변화, 크레딧 충전, 의견 처리를 알 수 없다. 푸시로 알리고, 놓쳐도 앱 안에서 다시 볼 곳(알림 화면)을 둔다. 공지는 같은 곳에서 탭으로 나눠 보여 준다.

**성공 기준**: 보호자가 앱을 닫아 둔 상태에서 이룸이가 일과를 끝내면 몇 초 안에 푸시가 오고, 누르면 그 이룸이의 홈이 열린다. 푸시를 꺼 두었거나 놓쳐도 종 아이콘의 빨간 점과 알림 화면으로 같은 내용을 볼 수 있다.

**실패로 보는 것 (기술적으로 동작해도)**
- 같은 일로 푸시가 여러 번 온다, 또는 매주 의미 없는 알림이 와서 보호자가 알림을 통째로 끈다.
- 푸시 문구에 보호자가 입력한 원문(일과 제목, 이룸이 이름)이 실린다.
- 푸시나 Firebase가 실패해서 일과 완료·초대 같은 본래 동작이 실패한다.
- 이룸이 기기에 보호자용 알림이 뜬다.

## 화면에서 정한 것 (사용자 합의)
- 받는 사람은 **보호자만**이다. 이룸이 기기에는 푸시를 보내지 않는다.
- 종 아이콘은 사용자가 준 에셋 `notification_bell.png`(노란 종, 짙은 남색 테두리, 투명 PNG)를 쓴다. 폰은 홈 상단에서 프로필 사진 왼쪽, 태블릿은 옆 패널의 ELUM 로고 오른쪽이다. 안 읽은 알림이나 공지가 있으면 빨간 점이 붙는다.
- 종을 누르면 알림 화면이 열리고 위에 **알림**, **공지사항** 두 탭이 있다. 각 탭에 안 읽음 점이 붙는다.
- 알림은 날짜별(오늘, 어제, 이전)로 묶고, 안 읽은 건 연한 민트 바탕이다. 누르면 해당 화면으로 이동한다.
- 공지사항 탭은 지금 홈에 뜨는 공지 팝업의 내용을 목록으로 다시 볼 수 있게 한다.
- 알림 설정: `모든 알림 받기` 하나와 종류별 켜고 끄기. 기기의 알림 권한이 꺼져 있으면 이유를 안내하고 `기기 설정 열기`를 준다. 거부해도 앱은 그대로 동작한다.
- 알림이 하나도 없을 때의 빈 화면은 따로 그린다. 가운데 그림은 `notifications_empty_lumi.png`(루미가 빈 알림함을 든 모습)를 쓴다.
- 광고·마케팅 알림은 없다. 그래서 수신 동의 화면도 필요 없다.
- 문구는 해요체, 용어는 `이룸이`·`기기`를 따른다. 실패에는 에러 코드를 보여 준다.

## 리마인더와의 관계
#777의 일과별 리마인더(`ReminderScheduler`, 기기 안 로컬 예약)는 **이 설계와 별개**다. 이번 작업에서 건드리지 않는다. 숨겨 둔 알림 줄(`_isReminderRowVisible=false`)도 그대로 둔다. 리마인더는 알림 목록에 기록하지 않고, 이 문서의 알림 설정 스위치와도 묶지 않는다.

## 알림 종류 5가지와 보내는 시점

| 종류 (코드) | 언제 | 누구에게 | 묶기 | 누르면 |
|---|---|---|---|---|
| 일과 완료 `ROUTINE_COMPLETED` | 이룸이가 일과의 마지막 카드를 체크한 순간 | 그 이룸이의 보호자 전원 | 이룸이·날짜별 1건. 같은 날 두 번째부터는 기존 알림을 고쳐 쓴다(개수 갱신, 다시 안 읽음, 맨 위로). 기기 알림도 같은 묶음 키로 바꿔 띄운다 | 그 이룸이의 홈 |
| 다른 보호자가 일과를 보냄 `ROUTINE_SENT_BY_CO_GUARDIAN` | 다른 보호자가 일과를 이룸이 홈에 올린 순간(새로 만들어 보내기, 일과관리에서 오늘 보내기 둘 다) | 그 이룸이의 보호자 중 **보낸 사람을 뺀** 전원 | 묶지 않음 | 그 이룸이의 홈 |
| 새 보호자 합류 `CO_GUARDIAN_JOINED` | 초대 암호로 합류가 끝난 순간 | 합류한 사람을 뺀 기존 보호자 전원 | 묶지 않음 | 함께하는 사람 화면 |
| 크레딧 다시 채움 `CREDIT_REFILLED` | 월요일 오전 9시(KST) 스케줄러 | **지난 주에 크레딧을 다 써서 0이 된 적 있는** 보호자만 | 주당 1건 | 크레딧 화면 |
| 의견 처리 완료 `FEEDBACK_RESOLVED` | 관리자가 의견 상태를 `처리 완료(DONE)`로 바꾼 순간 | 의견을 보낸 보호자 | 의견당 1건(다시 열었다 닫아도 다시 보내지 않음) | 알림 화면에 머무름(의견 목록 화면이 없으므로) |

받는 사람·개수 규칙 (제 판단)
- **요청한 사람은 받지 않는다** (5종 공통). 보호자 기기의 이룸이 화면에서 보호자 계정으로 체크해 끝낸 일과도 그 보호자 본인은 받지 않고 다른 보호자만 받는다. 이룸이 기기에서 끝낸 일과는 보호자 전원이 받는다.
- **일과 완료 개수는 그날 끝낸 서로 다른 일과 수**다. 묶음 행에 끝낸 일과 id 목록을 저장한다. 같은 일과의 마지막 카드를 해제했다가 다시 체크해도 개수가 늘지 않고 푸시도 다시 가지 않는다. 해제해도 개수에서 빼지 않는다.
- 완료 경로는 두 곳이다: 카드 한 장 체크(`completeStep`)와 오프라인 체크 반영(`syncProgress`). 둘 다 같은 완료 이벤트를 낸다. 오프라인 반영은 반영된 때 알린다(실시간 기준의 예외). 날짜는 반영 시각이 아니라 일과의 날짜를 쓴다.
- **"보냄"은 이룸이 홈에 일과가 올라가는 세 경로 모두**다: 새로 만든 일과의 승인(`RoutineService.confirm`, 만든 직후는 임시저장이라 홈에 안 뜬다), 일과관리에서 오늘 보내기(`RoutineLibraryService.send`), 지난 일과 다시하기(`RoutineService.duplicate`). 일과관리 복사하기는 홈에 안 뜨므로 제외.
- 이룸이 기기 요청의 `memberId`는 그 기기를 연결해 준 보호자다. "요청한 사람 빼기"는 보호자 기기 요청(`!caller.isElumi()`)일 때만 적용한다.
- 이룸이가 여럿인 보호자도 푸시 문구는 "이룸이가 …"로 둔다. 누구인지는 눌러서 열린 홈과 알림 목록에서 보인다(원문 보호 우선).

정한 이유 (제 판단, 일반 앱의 관례를 따름)
- **일과 완료**: 원래 합의는 "하루에 한 번만 묶어서"였다. 저녁에 모아서 보내는 방식은 실시간성이 떨어지므로, 첫 완료는 바로 알리고 같은 날 다음 완료는 같은 알림을 고쳐 쓰는 방식(메신저·배달 앱이 쓰는 묶음 알림)으로 정했다. 알림 목록에는 이룸이·날짜마다 한 줄만 남는다.
- **다른 보호자가 일과를 보냄**: "만듦" 대신 "보냄"을 기준으로 했다. 일과관리 전용 원본(`libraryOnly`)을 만들기만 한 것은 이룸이에게 영향이 없어 알리지 않는다.
- **크레딧**: 주간 지급은 계정을 조회할 때 채우는 방식(`ensureWeeklyGrant`)이라 지급 시점이 따로 없다. 매주 모두에게 보내면 소음이 되므로 지난 주에 모자랐던 사람에게만 아침에 알린다. 스케줄러는 지급을 미리 하지 않고 알림만 만든다(문구는 "이번 주 크레딧이 채워졌어요"이고 실제 지급은 다음 조회 때 일어나도 결과는 같다).
- **의견**: 관리자 답장 기능이 없어 상태 변경을 신호로 쓴다. 답장 기능은 만들지 않는다.

## 문구와 원문 보호
- 푸시와 목록 모두 **서버가 정한 문구 틀 + 서버가 아는 이름**으로 만든다. 이룸이 이름과 일과 제목은 사용자가 입력한 원문이다.
- **기기 알림(FCM)에는 원문을 넣지 않는다**(서비스 원칙 5). 예: "이룸이가 오늘 일과를 끝냈어요", "이룸이가 오늘 일과 2개를 끝냈어요".
- **앱 안 목록**은 앱이 로그인한 상태로 서버에서 가져오므로 원문을 보여 준다. 예: "하늘이가 '세수하기'를 끝냈어요". 서버는 알림 행에 원문을 복사하지 않고 일과·이룸이 id만 저장하며, 목록 응답을 만들 때 현재 이름을 붙인다. 일과나 이룸이가 지워졌으면 이름 없이 일반 문구로 보여 준다.
- 언어: 푸시 문구는 기기 토큰과 함께 저장한 기기 언어로 서버가 고른다(ko·en·ja·zh·es, 없으면 en). 목록 문구는 앱이 종류 코드와 값으로 ARB에서 만든다.

## 서버 (#827)

### 저장
- `notification`: 받는 보호자 id, 이룸이(profile) id(없을 수 있음), 종류 코드, 대상 id(일과 id 등), 묶음 키(예: `ROUTINE_COMPLETED:{profileId}:{yyyy-MM-dd}`), 개수, 만든 시각, 마지막으로 고친 시각, 읽은 시각. 받는 사람 + 묶음 키에 유일 제약을 걸어 같은 묶음이 두 줄 생기지 않게 한다.
- `push_device`: 보호자 id, FCM 토큰(유일), 플랫폼(ios/android), 기기 언어, 마지막 등록 시각.
- `notification_setting`: 보호자 id별 전체 켜짐 + 종류별 켜짐. 행이 없으면 모두 켜짐으로 본다.
- 공지 읽음: 보호자 id별 "공지 탭을 마지막으로 연 시각" 하나만 저장한다. 그보다 늦게 **보이기 시작한** 공지(게시 시작 시각, 또는 관리자가 다시 보이게 한 시각 중 늦은 것)가 있으면 공지 탭에 빨간 점이 붙는다. 언어·플랫폼 조건은 공지 목록과 같게 계산한다.
- 보관: 알림은 90일 지나면 지우는 스케줄러를 둔다. 회원 탈퇴 시 그 보호자의 알림·기기·설정은 기존 탈퇴 정리(`WithdrawnMemberPurgeScheduler`)와 같은 때 지운다.

### API (보호자 토큰만, 이룸이 기기 토큰은 403)
- `PUT /api/push-devices` 토큰 등록·갱신(같은 토큰이 다른 회원 것이면 옮겨 단다) / `DELETE /api/push-devices/{token}` 로그아웃 시 해제.
- `GET /api/notifications?cursor=&size=` 최신순 목록. 전체 보호자 단위이며 이룸이를 고르는 `X-Profile-Id`와 상관없이 모든 이룸이의 알림을 준다. 각 행에 이룸이 id·이름을 싣는다.
- `GET /api/notifications/unread-summary` 알림 안 읽음 여부·개수, 공지 안 읽음 여부(종 아이콘 빨간 점용).
- `GET /api/notices/history?cursor=&size=` 공지사항 탭 목록(로그인 필요). 지금의 공개 공지 API(`/api/app/notices`, 게시 중인 것 5개, 60초 캐시)는 홈 팝업용으로 그대로 두고, 탭은 게시가 끝난 공지까지 최근 90일을 언어·플랫폼 조건으로 준다.
- `POST /api/notifications/{id}/read`, `POST /api/notifications/read-all`, `POST /api/notices/seen`.
- `GET/PUT /api/notification-settings`.

### 발송 흐름
- 일이 일어난 트랜잭션이 **커밋된 뒤** 이벤트를 받아(`@TransactionalEventListener(AFTER_COMMIT)` + 비동기) 알림 행을 쓰고 푸시를 보낸다. 알림·푸시가 실패해도 본래 요청은 이미 성공했다. 서버에는 아직 이벤트·비동기 기반이 없으므로 `@EnableAsync`와 알림 전용 실행 스레드 풀 설정을 새로 만든다.
- 이벤트를 내는 곳: `completeStep`·`syncProgress`(완료), 일과 보내기 3경로(보냄), `ProfileInviteService.redeem`(합류), `FeedbackService.changeStatus`(처리 완료), 월요일 스케줄러(크레딧, 거래 기록의 `balanceAfter`로 지난 주 0 도달 판정).
- **알림 행은 설정과 상관없이 항상 쓴다.** 설정(전체·종류별)은 푸시를 보낼지만 정한다. 즉 푸시를 꺼도 앱 안 목록에는 남는다.
- 푸시 내용: `notification`(제목·본문, 원문 없음) + `data`(종류 코드, 알림 id, 이룸이 id, 대상 id). 일과 완료는 묶음 키로 Android `tag`·iOS `apns-collapse-id`를 줘서 기기에서도 한 줄로 바뀌어 보이게 한다.
- FCM 응답이 `UNREGISTERED`·`INVALID_ARGUMENT`(토큰 문제)면 그 토큰 행을 지운다. 그 밖의 실패는 로그만 남기고 다시 보내지 않는다.
- Firebase 키 파일이 없으면(로컬·테스트) 푸시 발송만 건너뛰는 빈 발송기를 쓴다. 알림 행은 그대로 쓰므로 목록 기능은 Firebase 없이 확인할 수 있다.
- 로그: `[notification push] sent type=... devices=n`, `[notification push] failed : {FCM 오류 코드}` 형식. 토큰 원문과 문구 원문은 남기지 않는다.

## 클라 화면 (#826)
- 종 아이콘·빨간 점: 홈 진입과 앱이 다시 앞으로 올 때, 푸시를 받았을 때 `unread-summary`를 다시 받는다. 실패하면 점 없이 종만 보여 주고 조용히 넘어간다(종을 누르면 목록 화면에서 실패를 보여 준다).
- 알림 탭: 무한 스크롤 목록, 오늘/어제/이전 묶음, 안 읽음 민트 바탕, 누르면 읽음 처리 후 이동. 위에 "모두 읽음" 버튼. 실패하면 다시 시도와 에러 코드, 0건이면 빈 화면 그림.
- 공지사항 탭: 지금 공지 API로 목록을 보여 준다. 탭을 열면 `notices/seen`을 보낸다. 홈 공지 팝업 동작은 바꾸지 않는다.
- 이룸이가 여럿이면 각 행에 이룸이 이름을 작게 붙인다. 누르면 지금 보는 이룸이를 그 이룸이로 바꾼 뒤 이동한다. 그 이룸이에 더는 접근할 수 없으면(나갔거나 지워짐) 이동하지 않고 안내 팝업을 띄운다.
- 알림 설정 화면: 보호자 설정 안에 둔다. 전체 + 5종 스위치, 서버에 저장한다. 기기 권한이 꺼져 있으면 위에 안내 줄과 `기기 설정 열기`를 둔다.
- 이 이슈만 끝나도(푸시 없이) 목록·빨간 점·설정이 동작해야 한다.

### Firebase 준비 상태 (2026-10-19 콘솔 확인)
- 프로젝트 `elum-dd083`(번호 527289510534). Android·iOS 앱 둘 다 `kr.twinfang.elum`으로 등록돼 있다.
- FCM HTTP v1 API 켜짐. APNs 인증 키(개발·프로덕션, 키 ID `KDLNX666L7`, 팀 `CUK22HY6YC`) 업로드돼 있다.
- 설정 파일 2개와 서버 서비스 계정 키를 받아 레포 밖 `~/.elum-secrets/firebase-elum-dd083/`(본인만 읽기)에 두었다. 다운로드 폴더의 `elum-1a20d-…json`은 다른 프로젝트 것이라 쓰지 않는다.
- 구현 때 할 일: 세 파일 경로를 `.gitignore`에 먼저 더한 뒤 제자리(`client/android/app/google-services.json`, `client/ios/Runner/GoogleService-Info.plist`, `server/src/main/resources/firebase-adminsdk.json`)에 복사. 서버 CI의 주석 처리된 `FIREBASE_ADMINSDK_JSON` 단계를 살리고, iOS TestFlight 워크플로우에 plist 생성 단계를 더하고, 해당 GitHub Secret(`FIREBASE_ADMINSDK_JSON`, `GOOGLE_SERVICES_JSON`, iOS plist)을 등록한다. iOS Xcode 프로젝트에 Push Notifications·Background Modes(remote notification) 권한을 켠다.
- **권한 요청 시점**: 앱을 처음 켤 때는 묻지 않는다. 보호자 온보딩이 끝나고 처음으로 일과를 이룸이에게 보낸 직후, 앱 안 안내 시트("이룸이가 일과를 끝내면 알려 드릴까요?")를 먼저 띄우고 `알림 받기`를 누르면 그때 OS 권한 창을 띄운다(iOS, Android 13 이상). `나중에`를 누르면 다시 묻지 않고, 알림 설정 화면에서 켤 수 있다.
- **토큰**: 보호자로 로그인했고 권한이 있을 때 등록한다. 토큰이 바뀌면 다시 등록하고, 로그아웃·탈퇴, 그리고 기기 역할을 이룸이 기기로 바꿀 때(`AppRole`을 바꿔 연결 암호로 이룸이 계정이 될 때) 해제한다. 이룸이 기기는 등록하지 않는다.
- **보호자 기기를 잠깐 이룸이 화면으로 돌렸을 때**(비밀암호 전환, 계정은 보호자 그대로): 토큰은 해제하지 않는다(건네준 동안에도 보호자 알림을 놓치지 않게). 대신 앱이 켜져 있는 동안 배너를 띄우지 않는다. 앱이 뒤에 있을 때의 OS 알림은 그대로 온다.
- **앱이 켜져 있을 때 (보호자 화면)**: 기기 알림 배너를 그대로 띄우고(iOS 전경 표시, Android는 로컬 알림으로 띄움) 빨간 점을 갱신한다.
- **누르면**: 앱이 꺼져 있었든 뒤에 있었든 `data`로 알림 화면과 같은 이동 규칙을 따른다. 로그인이 풀려 있으면 로그인 후 홈으로 간다.
- Android 알림 채널은 하나(`guardian_updates`, "보호자 알림")만 만든다. #777 리마인더 채널과 나눈다.

## 실패 경로 요약
| 상황 | 동작 |
|---|---|
| Firebase 키 없음·FCM 장애 | 푸시만 빠지고 알림 목록·빨간 점은 정상 |
| 기기 권한 거부 | 앱 정상, 알림 설정 화면에 안내와 `기기 설정 열기` |
| 목록 불러오기 실패 | 다시 시도 + 에러 코드 (`E-NOTIF-LIST`) |
| 읽음 처리 실패 | 화면에서는 읽음으로 보이고 다음 새로고침 때 서버 값으로 맞춤, 이동은 그대로 진행 |
| 설정 저장 실패 | 스위치를 원래대로 돌리고 실패 팝업 + 에러 코드 (`E-NOTIF-SETTING`) |
| 누른 알림의 이룸이에 접근 불가 | 이동하지 않고 안내 팝업 |
| 알림 대상(일과)이 지워짐 | 이름 없는 일반 문구로 표시, 누르면 그 이룸이 홈 |

## 테스트가 겨누는 결함
- 같은 날 일과 두 개 완료 시 알림이 두 줄이 된다 → 서버 묶음 키 테스트.
- 같은 일과를 해제했다 다시 끝내면 개수가 늘고 푸시가 또 간다 → 일과 id 목록 테스트.
- 오프라인 반영(`syncProgress`)으로 끝낸 일과는 알림이 안 생긴다 → 두 완료 경로 테스트.
- 일과를 보낸 보호자 자신에게 알림이 간다 → 받는 사람 계산 테스트.
- 푸시 본문에 일과 제목·이룸이 이름이 들어간다 → 푸시 문구 생성 테스트.
- 푸시 실패가 일과 완료 요청을 실패시킨다 → 발송기가 예외를 던져도 완료 API가 200인지 테스트.
- 푸시를 끈 사람의 목록에서도 알림이 빠진다 → 설정과 행 쓰기 분리 테스트.
- 이룸이 기기 토큰으로 기기 등록이 된다 → API 403 테스트.
