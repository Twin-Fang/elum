# 구형 비밀번호 가입/로그인 운영 차단 설계

## 배경

중간 심사 이전 APK는 이룸이 이름을 아이디로, 고정 비밀번호를 비밀번호로 사용해 계정을 만들었다.
현재 앱은 소셜 로그인만 사용하지만 서버의 비밀번호 가입/로그인 API가 남아 있어 구형 APK가 운영 DB에
계정을 다시 만들 수 있었다.

## 결정

- `POST /api/auth/signup`, `POST /api/auth/login`은 제거 예정 API로 표시한다.
- 두 API를 별도 컨트롤러로 분리하고, 운영이 아닌 프로필에서
  `elum.auth.legacy-password.enabled=true`일 때만 매핑한다.
- 설정 기본값은 `false`로 둔다. 운영 설정에 키가 없어도 닫힌 상태가 안전하게 유지된다.
- 소셜 로그인, 토큰 갱신, 로그아웃 API는 기존 컨트롤러에 남겨 영향을 분리한다.
- 구형 비밀번호 인증 E2E는 로컬 주소에서만 실행하고, 서버를 명시적으로 활성화했을 때만 사용한다.

## 정상 흐름

1. 운영 서버가 기본 설정으로 시작한다.
2. 구형 비밀번호 인증 컨트롤러 빈이 생성되지 않는다.
3. 구형 APK가 가입 또는 로그인을 요청하면 매핑이 없어 404를 받는다.
4. 현재 앱의 소셜 로그인과 토큰 API는 기존과 같이 동작한다.

## 개발/E2E 흐름

1. 개발자가 로컬 서버에 `ELUM_AUTH_LEGACY_PASSWORD_ENABLED=true`를 명시한다.
2. 구형 컨트롤러가 생성되고 가입/로그인 회귀 시험을 실행할 수 있다.
3. E2E 도구는 localhost 또는 127.0.0.1 이외 주소를 거부해 운영 서버 오사용을 막는다.

## 실패 경로와 방어

- 설정 누락: 기본값이 `false`이므로 API가 열리지 않는다.
- 운영 환경변수 오설정: `prod` 프로필 차단이 먼저 적용돼 설정값과 무관하게 API가 열리지 않는다.
- 구형 APK 요청: 계정 생성 없이 404로 끝난다.
- 운영 주소로 구형 E2E 실행: 도구가 요청 전에 실패한다.
- 소셜 인증 회귀: 비밀번호 메서드를 기존 인증 컨트롤러에서 분리해 소셜/토큰 매핑은 건드리지 않는다.

## 검증

- 기본 설정에서 구형 컨트롤러 빈이 없는지 테스트한다.
- 설정을 명시적으로 켰을 때만 빈이 생기는지 테스트한다.
- `prod` 프로필에서는 설정을 켜도 빈이 생기지 않는지 테스트한다.
- 전체 서버 테스트를 실행해 소셜 인증과 기존 기능 회귀가 없는지 확인한다.
