# 0. 이 발표의 목적

> ⚠️ **중간심사 점수는 최종 순위에 반영되지 않는다.**

목적은 점수가 아니라 **피드백을 정확히 받아오는 것**이다.
전년도 수상작 토닥이는 중간심사에서 *"타겟 명확화가 필요하다"* 는 지적을 받고
타겟을 좁히고 관리자 모드를 추가해 **보건복지부장관상**을 받았다.

**우리는 지적을 미리 받아 이미 한 사이클 돌았다.** 그걸 보여주는 것이 이 발표의 핵심이다.

| 2025 | **토닥이** (보건복지부장관상) | 발달장애 → **일상 예측 가능성** |

> **장관상은 "장애인을 위한 범용 앱"이 아니라
> 특정 장애 특성에서 나오는 문제 하나를 아주 좁게 잡은 팀이 받았다.**

## 그래서 ELUM의 문제 정의를 좁힌다

```
❌ 넓다   "발달장애인의 일상생활을 돕는 앱"
✅ 좁다   "보호자가 매일 머릿속으로 하던 과제분석을 AI가 대신한다"
```

**이 한 문장이 발표 전체를 관통해야 한다.** 모든 슬라이드가 이걸 뒷받침한다.

# 2. 슬라이드 구성 (13장)

| # | 슬라이드 | 핵심 내용 | 시간 | 심사항목 |
| --- | --- | --- | ---: | --- |
| 1 | 표지 | [룸룸] 이룸 · 분야 1 디지털 포용 | — | — |
| 2 | **한 문장** | *"'학교 갈 준비해' 한 마디를 아이가 따라 할 수 있는 순서로 바꿉니다"* | 0:30 | — |
| 3 | **문제** | 그 한 마디에 숨은 8단계 · 보호자가 매번 직접 쪼갠다 | 1:00 | 필요성 |

| 6 | **유사 사례 비교** | 종이카드 · 일정앱 · **토닥이** · 해외앱 · 범용 LLM | 1:00 | **참신성** ★ |
| 7 | **시연 영상** | 입력 → 카드 생성 → 보상 설정 → 승인 → 아이 수행 | 2:30 | 완성도 |
| 8 | 핵심기술 ① | **과제분석 자동화** — 한 문장 → 행동 단계 | 0:50 | 참신성 |
| 9 | 핵심기술 ② | **캐릭터 일관 삽화** — 매 단계 같은 캐릭터 | 0:40 | 참신성 |
| 10 | **전문가 자문 → 반영** | 지적 4건 → 바꾼 것 4건 (대조표) | 1:20 | **적용가능성** ★ |
| 11 | **장애와 개발물의 연관성** | 과제분석·연쇄·강화 1:1 매핑 | 0:50 | **적용가능성** ★ |
| 12 | 상용화 · 리스크 | 활용 방안 · 제약과 해결 | 0:40 | 기대효과 |

**합계 10분.** 부록으로 플로우차트·메뉴구조도를 뒤에 붙인다(발표에선 넘기고 질의 때 사용).

> 대회 필수 항목인 **플로우차트·메뉴구조도**는 자료집에 반드시 포함되어야 하지만,
> 발표 10분 안에 설명할 필요는 없다. **부록에 두고 제출물 요건을 채운다.**

# 3. 장별 작성 지침

## 2장 — 한 문장 (가장 중요)

심사위원이 이 슬라이드만 보고 서비스를 이해해야 한다.

```
"학교 갈 준비해" 한 마디를
아이가 따라 할 수 있는 순서로 바꿉니다

        [ 한 문장 ]  →  [ 카드 5장 이미지 ]
```

**기능을 나열하지 않는다.** 앱 스크린샷도 아직 넣지 않는다.

## 3장 — 문제 (구체적 장면으로)

```
"학교 갈 준비해"

  옷 입기 → 가방 챙기기 → 준비물 확인 → 신발 신기
  → 집 나서기 → 정류장 가기 → 버스 타기 → 학교 도착

이 한 마디에 8단계가 숨어 있습니다.
아이는 한 번에 이해하기 어렵고,
보호자는 매일 아침 이걸 머릿속에서 쪼개 설명합니다.
```

> 비 오는 날에는 우비·장화가 더 붙는다는 점까지 말하면
> **"상황마다 달라진다"** 는 진짜 문제가 드러난다.

## 4장 — 문제의 크기 (통계)

| 숫자 | 출처 |
| --- | --- |
| 등록 발달장애인 **약 25만 명**, 그중 **22.5%**가 일상생활 도움 필요 | 보건복지부, 2021년 발달장애인 실태조사 |
| 보호자의 **68.8%가 부모** | 동일 |
| **보호자 우울 점수 19.43** — 우울증 의심 기준(16) 초과 | 동일 |

> 🎯 **마지막 숫자를 설계 근거로 연결한다.**
> *"그래서 저희는 보호자에게 무언가를 더 시키지 않는 방향으로 설계했습니다.
> 온보딩은 네 단계를 넘지 않고, 보상 설정도 건너뛸 수 있습니다."*

숫자를 보여주고 끝내는 팀은 많다. **그 숫자로 우리가 무엇을 하지 않았는지**까지 말하는 팀은 드물다.

## 5장 — 대상 (자문 반영의 첫 증거)

```
처음 정의    7~12세 발달장애 아동
                  ↓
자문         "생활연령과 발달연령은 다릅니다"
통계         지적장애인 중위연령 33.8세 — 절반이 성인
                  ↓
다시 정의    행동 카드의 시각정보와 순서를
             이해할 수 있는 발달장애인
```

**자문 → 통계 → 설계 변경**이 한 장에 들어간다. 이 구조가 10장에서 반복된다.

## 6장 — 유사 사례 비교 ★ 참신성 20점

| 비교 대상 | 한계 |
| --- | --- |
| 종이 그림카드 · PECS | 상황마다 준비물이 달라 **매번 새로 만들어야** |
| 일정관리 앱 | 일정은 알려주지만 **행동 단계로 쪼개지 않는다** |
| **토닥이** (2025 보건복지부장관상) | **정해진 일정**을 예측 가능하게 보여줌 — 일정을 **만들어내는 앞단**이 없음 |
| 해외 앱 (Choiceworks, First Then Visual Schedule) | 카드를 **사람이 직접 만들어야** · 한국어·국내 맥락 부재 |
| 범용 LLM (ChatGPT 등) | 카드·이미지·수행 흐름이 없고 **보호자 승인 구조**가 없음 |

> ⚠️ **토닥이를 우리가 먼저 꺼낸다.** 심사위원이 먼저 말하게 두면 방어가 되고,
> 우리가 먼저 말하면 **분석한 팀**이 된다.

## 7장 — 시연 영상 (2분 30초)

**현장 실시간 시연은 하지 않는다.** 네트워크·AI 응답 지연으로 배점이 날아간다.

```
보호자 온보딩 → 일과 입력 → AI 추가 질문
→ 보상 설정 → 카드 생성 → 검토·승인
→ 아이 모드 → 카드 수행 → 완료·보상
```

실기기 녹화 · **자막 필수** · 나레이션 없음(발표자가 설명) · 카드 생성 순간 2초 정지

## 10장 — 전문가 자문 → 반영 ★ 우리만의 무기

| 소장님 지적 | 우리가 바꾼 것 |
| --- | --- |
| *"기분이 나쁘면 폰을 던지지 속으로 다스리지 않는다"* | 추천 일과에서 내면 조절 항목 **전부 제거**, AI 프롬프트에 규칙 추가 |
| *"아들이 회사 다니는데 '학교에 가요'가 뜬다"* | 성인 일과 8개 추가 · **타겟 재정의** |
| *"강화(보상)가 없으면 행동하지 않는다"* | **보상 설정·수행 중 지속 노출** 구현 |
| *"단계 수가 고정이면 안 된다"* | 카드 수 고정 **해제** |

> 역대 어느 팀도 **중간심사에서** "전문가에게 검증받고 이미 고쳤다"를 말하지 못했다.
> 토닥이는 중간심사에서 **지적을 받고** 바꿨고, 우리는 **미리 받아서** 바꿨다.

## 11장 — 장애와 개발물의 연관성 ★ 장애인 전문가 3명 겨냥

```
과제분석(Task Analysis)  →  AI가 한 문장을 행동 단계로 분해
연쇄(Chaining)           →  카드를 순서대로 수행
강화(Reinforcement)      →  보호자가 정한 보상을 상기
개별화                   →  보호자가 카드를 추가·삭제·수정
```

> ⚠️ **"ABA 기반 치료 앱"이라고 하지 않는다.**
> *"ABA 및 특수교육에서 활용되는 과제분석·강화·연쇄 원리를 참고했습니다"* 로 말한다.
> 금지 표현은 [발표 표현 가이드](./발표_표현가이드.md) 참고.

## 13장 — 기대효과 + 고민 중인 것

마지막에 **심사위원께 묻고 싶은 것**을 한 칸 둔다.

```
저희가 지금 고민하고 있는 것

· 보호자가 카드를 수정하는 부담과 AI 정확도 사이의 균형
· 성인 사용자를 위한 화면 톤 — 캐릭터를 유지할지
· 실증에서 어떤 지표를 봐야 의미가 있을지
```

> **중간심사의 목적은 피드백이다.** 우리가 원하는 주제로 질문을 유도할 수 있고,
> "고민하고 있다"는 태도 자체가 적용가능성 점수에 유리하게 작용한다.

# 4. 슬라이드에서 피해야 할 것

| 하지 말 것 | 이유 |
| --- | --- |
| 기능 나열 슬라이드 | "무엇을 만들었나"보다 "무엇을 푸나"가 먼저다 |
| DLP·암호화 강조 | **보안 대회가 아니다.** 리스크 슬라이드에서 한 줄만 |
| "ABA 기반 치료 앱" | 임상 검증이 없다. 근거를 요구받는다 |
| 개발 기간·커밋 수 자랑 | 심사 항목에 없다 |
| 글자 빽빽한 장표 | 10분에 13장이면 장당 46초다 |
