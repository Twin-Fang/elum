# 소셜 로그인 설정 가이드 (카카오 · 네이버 · 구글 · 애플)

서버 구현은 끝났다. 남은 것은 **각 제공자 콘솔에서 앱을 등록하고 키를 받아
서버 설정에 넣는 일**이다. 이 문서는 그 순서를 콘솔 화면 단위로 적는다.

앱 식별자는 안드로이드·iOS 모두 `kr.twinfang.elum`이다.

---

## 0. 먼저 정할 것 — Firebase를 쓸 것인가

결론부터: **쓰지 않는 쪽을 권한다.**

Firebase Authentication은 구글·애플은 기본 지원하지만 **카카오·네이버는 지원하지 않는다.**
네 개를 다 지원하려면 카카오·네이버는 어차피 서버가 직접 검증한 뒤
Firebase Custom Token을 따로 만들어 줘야 한다. 그러면 로그인 경로가 두 갈래로 갈라진다.

| | 서버 직접 검증 (현재 구현) | Firebase Authentication |
|---|---|---|
| 카카오·네이버 | 서버가 검증 | **서버가 검증 + 커스텀 토큰 발급** (이중 작업) |
| 구글·애플 | 서버가 ID 토큰 서명 검증 | Firebase가 검증 |
| 서버 추가 작업 | 없음 (구현 완료) | Admin SDK 도입, 토큰 종류별 분기 |
| 앱 추가 작업 | 제공자 SDK 4종 | 제공자 SDK 4종 + firebase_auth |
| 제공자 콘솔 작업 | 아래 1~4절 그대로 | 아래 1~4절 **그대로 + Firebase 콘솔 추가** |

**제공자 콘솔에서 할 일은 어느 쪽이든 똑같다.** Firebase를 쓴다고 카카오 앱 등록이
사라지지 않는다. 그래서 1~4절을 먼저 하고, Firebase는 5절에서 선택하면 된다.

> 참고 — 현재 이 저장소에 Firebase Authentication은 들어 있지 않다.
> `client/pubspec.yaml`에 `firebase_auth`가 없고 `google-services.json`도 없다.
> CI에 있는 `PROJECT-FLUTTER-ANDROID-FIREBASE-CICD`는 테스터 배포(App Distribution)용이라
> 로그인과 무관하다.

| 앱 카테고리 | 교육 | — |

### 서명 지문은 문서에 적지 않는다

SHA-1과 키 해시는 **아래 명령으로 그때그때 뽑아 쓴다.** 저장소에 적어 두지 않는다.
비밀값은 아니지만(APK에서 추출 가능) 공개 저장소에 굳이 남길 이유가 없다.

```bash
# 구글용 SHA-1 — 디버그
keytool -list -v -keystore ~/.android/debug.keystore -alias androiddebugkey \
  -storepass android -keypass android | grep "SHA1:"

# 구글용 SHA-1 — 릴리스 (경로·alias·비밀번호는 android/key.properties에 있다)
keytool -list -v -keystore client/android/app/keystore/key.jks \
  -alias <keyAlias> | grep "SHA1:"

# 카카오용 키 해시 — 디버그
keytool -exportcert -alias androiddebugkey -keystore ~/.android/debug.keystore \
  -storepass android -keypass android | openssl sha1 -binary | openssl base64

# 카카오용 키 해시 — 릴리스
keytool -exportcert -alias <keyAlias> -keystore client/android/app/keystore/key.jks \
  | openssl sha1 -binary | openssl base64
```

Play 앱 서명(Play App Signing)을 켜면 Play Console이 서명 키를 새로 만든다.
그때는 **Play Console > 설정 > 앱 서명**의 SHA-1로 구글 클라이언트를 하나 더 만들어야 한다.

### 아직 없는 것

| 항목 | 언제 필요한가 |
|---|---|
| **iOS URL Scheme 등록** | 네이버 로그인. `Info.plist`에 `CFBundleURLTypes`가 아직 없다 |
| **Play Store 링크** | 스토어 출시 후. 지금은 미출시 URL 형식으로 등록해 둔다 |
| **App Store Apple ID** | 네이버 iOS 환경의 다운로드 URL |

## 1. 카카오

### 콘솔
https://developers.kakao.com/console/app

### 순서

1. **애플리케이션 추가하기** — 앱 이름 `이룸`, 회사명 입력
2. **앱 설정 > 앱 키** 로 이동
   - `네이티브 앱 키` → 앱(Flutter)에서 사용
   - **`앱 ID`(숫자)** → **서버 설정에 넣을 값**
3. **앱 설정 > 플랫폼**
   - Android 등록: 패키지명 `kr.twinfang.elum`, 키 해시 등록(아래 명령으로 추출)
   - iOS 등록: 번들 ID `kr.twinfang.elum`
4. **제품 설정 > 카카오 로그인** → 활성화 상태 **ON**
   (앱 로그인만 쓰면 Redirect URI는 필요 없다. 웹을 붙일 때만 등록한다.)
5. **제품 설정 > 카카오 로그인 > 동의항목**
   - 닉네임: 필수 동의
   - 카카오계정(이메일): **선택 동의**
     - 필수 동의로 받으려면 비즈니스 앱 전환이 필요하다.
     - 선택 동의면 이메일이 아예 안 올 수 있는데, 서버는 그래도 동작한다
       (계정을 찾는 키가 이메일이 아니라 카카오 회원번호이기 때문이다).

### 키 해시 추출

```bash
# 디버그
keytool -exportcert -alias androiddebugkey -keystore ~/.android/debug.keystore \
  -storepass android -keypass android | openssl sha1 -binary | openssl base64

# 릴리스 (실제 keystore 경로·alias로 바꿔 실행)
keytool -exportcert -alias <alias> -keystore <keystore.jks> \
  | openssl sha1 -binary | openssl base64
```

디버그와 릴리스 둘 다 등록한다. 하나만 등록하면 개발 중엔 되는데 배포 APK에서 로그인이 막힌다.

### 서버에 넣을 값

```yaml
oauth:
  kakao:
    app-id: 1234567      # 앱 키 페이지의 "앱 ID" 숫자
```

이 값이 하는 일 — 카카오가 준 토큰이 **우리 앱을 위해 발급된 것인지** 확인한다.
비워 두면 다른 앱 토큰으로도 우리 계정에 들어올 수 있어서, 서버는 비어 있으면 로그인을 거부한다.

## 2. 네이버

### 콘솔
https://developers.naver.com/apps/#/register

### 순서

1. **애플리케이션 등록**
   - 애플리케이션 이름: `이룸`
   - 사용 API: **네이버 로그인** 선택
   - 제공 정보 선택: 이메일 주소, 별명 (필요한 것만)
2. **로그인 오픈 API 서비스 환경**
   - `Android` 추가: 다운로드 URL(스토어 링크), 패키지명 `kr.twinfang.elum`
   - `iOS` 추가: URL Scheme(예: `elum`), 번들 ID `kr.twinfang.elum`
3. 등록을 마치면 **Client ID**, **Client Secret** 이 발급된다

### 서버에 넣을 값

```yaml
oauth:
  naver:
    client-id: xxxxxxxxxxxxxxx
    client-secret: xxxxxxxxxx
```

### 알아 둘 한계

네이버는 카카오의 `app_id`나 구글의 `aud`처럼 **"이 토큰이 어느 앱 것인지" 알려 주는 값을 주지 않는다.**
다른 네이버 앱에서 받은 액세스 토큰으로도 사용자 정보 조회가 성공한다.
프로토콜상 토큰만으로는 앱을 특정할 수 없다.

없애려면 앱이 액세스 토큰 대신 **인가 코드**를 보내고 서버가 client_secret으로 교환하는
방식으로 바꿔야 한다. 그래서 지금 쓰지 않더라도 client-secret을 미리 받아 둔다.
(코드는 `NaverOAuthVerifier` 주석에 같은 내용을 남겨 두었다.)

## 3. 구글

### 콘솔
https://console.cloud.google.com/apis/credentials

### 순서

1. 프로젝트 생성 (이미 Gemini API용 프로젝트가 있으면 그걸 써도 된다)
2. **API 및 서비스 > OAuth 동의 화면**
   - User Type: 외부
   - 앱 이름 `이룸`, 사용자 지원 이메일, 개발자 연락처
   - 범위: `email`, `profile`, `openid`
3. **사용자 인증 정보 > 사용자 인증 정보 만들기 > OAuth 클라이언트 ID** — **세 개를 만든다**

   | 유형 | 입력값 | 용도 |
   |---|---|---|
   | Android | 패키지명 `kr.twinfang.elum` + SHA-1 지문 | 안드로이드 앱 |
   | iOS | 번들 ID `kr.twinfang.elum` | iOS 앱 |
   | **웹 애플리케이션** | 이름만 (예: `ELUM 서버`) | **안드로이드가 ID 토큰을 받을 때 쓴다** |

> 웹 클라이언트를 왜 만드나 — 안드로이드의 `google_sign_in`은 `serverClientId`에
> **웹 클라이언트 ID**를 넣어야 ID 토큰을 발급한다. 그러면 그 토큰의 `aud`가 웹 클라이언트 ID가 된다.
> 이걸 모르면 "안드로이드에서 idToken이 null" 로 막힌다.

### SHA-1 지문 추출

```bash
# 디버그
keytool -list -v -keystore ~/.android/debug.keystore \
  -alias androiddebugkey -storepass android -keypass android | grep SHA1

# 릴리스
keytool -list -v -keystore <keystore.jks> -alias <alias> | grep SHA1
```

Play 앱 서명(Play App Signing)을 쓰면 **Play Console > 설정 > 앱 서명**에 있는
SHA-1도 함께 등록해야 한다. 업로드 키와 서명 키가 다르기 때문이다.

### 서버에 넣을 값

```yaml
oauth:
  google:
    client-ids:
      - 1234-web.apps.googleusercontent.com    # 웹 (안드로이드 로그인이 이걸로 온다)
      - 5678-ios.apps.googleusercontent.com    # iOS
```

**둘 다 넣는다.** 하나만 넣으면 다른 플랫폼 로그인이 전부 막힌다.
(안드로이드 클라이언트 ID는 `aud`로 오지 않으므로 넣을 필요가 없다.)

## 4. 애플

### 현재 상태
앱이 이미 **TestFlight에 올라가 있다.** 그래서 App ID·프로비저닝·Team ID는 이미 있고,
**Sign In with Apple 권한만 켜면 된다.**

- Apple Team ID: `ios/ExportOptions.plist`의 `teamID` 값
- Bundle ID: `kr.twinfang.elum` (이미 등록됨)

### 순서

1. https://developer.apple.com/account/resources/identifiers/list
   → `kr.twinfang.elum` 클릭 → Capabilities 목록에서 **Sign In with Apple** 체크 → **Save**
2. Xcode에서 `client/ios/Runner.xcworkspace` 열기
   → Runner 타겟 > **Signing & Capabilities** > `+ Capability` > **Sign In with Apple**
3. **프로비저닝 프로파일을 새로 받는다.**
   권한을 추가하면 기존 프로파일이 무효가 된다. Xcode 자동 서명이면 자동으로 갱신되고,
   수동 서명이면 developer.apple.com에서 프로파일을 다시 만들어 내려받아야 한다.
   CI로 빌드한다면 Secret에 넣어 둔 프로파일도 교체해야 한다.
4. **새 빌드를 TestFlight에 올린다.**
   지금 올라가 있는 빌드에는 이 권한이 없어서 애플 로그인이 동작하지 않는다.

### (선택) 안드로이드에서도 애플 로그인을 지원할 때

안드로이드는 네이티브 SDK가 없어 웹뷰로 로그인한다. 그래서 Services ID가 따로 필요하다.

1. **Identifiers > Services IDs** > `+` → 식별자 `kr.twinfang.elum.web`
2. Sign In with Apple 구성 → Domains and Subdomains, Return URLs 등록
3. 서버 `bundle-ids`에 이 Services ID도 함께 넣는다

### 서버에 넣을 값

```yaml
oauth:
  apple:
    bundle-ids:
      - kr.twinfang.elum          # iOS 네이티브
      # - kr.twinfang.elum.web    # 안드로이드까지 지원할 때만
```

### 알아 둘 특성

- **이메일 숨기기** — 사용자가 켜면 `xxxx@privaterelay.appleid.com` 주소가 온다.
  앱마다 다른 주소라 이메일로 사람을 식별할 수 없다. 서버는 `sub`로만 계정을 찾는다.
- **이름은 최초 로그인 때만 온다.** 두 번째부터는 주지 않는다.
- 심사 규정상 **다른 소셜 로그인을 제공하는 iOS 앱은 애플 로그인도 제공해야 한다.**
  카카오만 넣고 애플을 빼면 앱스토어 심사에서 반려된다.

## 5. (선택) Firebase Authentication을 쓸 경우 추가 작업

0절에서 Firebase를 쓰기로 정했을 때만 한다. 1~4절은 그대로 다 해야 한다.

### 콘솔
https://console.firebase.google.com

1. 프로젝트 만들기 → Android 앱(`kr.twinfang.elum`), iOS 앱(`kr.twinfang.elum`) 등록
   - `google-services.json` → `client/android/app/`
   - `GoogleService-Info.plist` → `client/ios/Runner/`
2. **Authentication > Sign-in method**
   - **Google**: 켜기만 하면 된다 (Firebase가 클라이언트를 자동 생성)
   - **Apple**: 켠 뒤 아래를 입력한다
     - Services ID (4절에서 만든 것)
     - Apple Team ID (developer.apple.com 우측 상단)
     - Key ID + Private Key — Certificates, Identifiers & Profiles > **Keys**에서
       "Sign in with Apple" 용 키를 만들고 받은 `.p8` 파일
   - **카카오 · 네이버**: **목록에 없다.** Custom Auth로 처리해야 한다
3. 앱에 `firebase_core`, `firebase_auth` 추가 후 `flutterfire configure`
4. 서버에 Firebase Admin SDK 추가
   ```gradle
   implementation 'com.google.firebase:firebase-admin:9.x.x'
   ```
   `FirebaseAuth.getInstance().verifyIdToken(idToken)` 으로 검증
5. 카카오·네이버는 서버가 검증 후 `createCustomToken(uid)`를 만들어 앱에 주고,
   앱이 `signInWithCustomToken()`으로 Firebase 세션을 얻는다

> 4·5번이 "Firebase를 써도 서버 검증 코드가 그대로 필요한" 지점이다.
> 이 작업량 때문에 0절에서 쓰지 않는 쪽을 권했다.

## 6. 받은 키를 어디에 넣는가

**서버와 앱이 방식이 다르다.** 두 군데 모두 넣어야 한다.

### 6-1. 서버 — GitHub Secret `APPLICATION_PROD_YML`

서버는 `.env`를 쓰지 않는다.
`.github/workflows/PROJECT-SPRING-CICD.yaml`이 배포할 때
**Secret `APPLICATION_PROD_YML`의 내용을 그대로 `application-prod.yml`로 떨군다.**
컨테이너에는 `TZ`와 `SPRING_PROFILES_ACTIVE`만 넘어간다.

`https://github.com/Twin-Fang/elum/settings/secrets/actions` → `APPLICATION_PROD_YML` 편집 →
아래 블록을 맨 아래에 추가한다. (저장소의 `application-prod.yml`에는 플레이스홀더로
들어가 있으므로, 시크릿에는 실제 값을 적는다.)

```yaml
oauth:
  timeout-millis: 5000
  kakao:
    app-id: "카카오 앱 ID 숫자"
  naver:
    client-id: "네이버 Client ID"
    client-secret: "네이버 Client Secret"
  google:
    client-ids:
      - "웹 클라이언트 ID.apps.googleusercontent.com"
      - "iOS 클라이언트 ID.apps.googleusercontent.com"
  apple:
    bundle-ids:
      - kr.twinfang.elum
```

로컬 개발은 `application-dev.yml`의 같은 블록에 넣거나 환경변수로 넘긴다.

```bash
OAUTH_KAKAO_APP_ID=1234567 \
OAUTH_GOOGLE_CLIENT_IDS=web-id.apps.googleusercontent.com,ios-id.apps.googleusercontent.com \
./gradlew bootRun --args='--spring.profiles.active=dev'
```

### 6-2. 앱 — `client/.env` (배포는 Secret `CLIENT_ENV_FILE`)

앱은 `flutter_dotenv`로 `.env`를 읽는다. 키 이름은 `client/.env.example`이 문서이고,
코드에서는 `AppConfig`를 통해서만 읽는다(위젯이 `dotenv.env[...]`를 직접 보지 않는다).

```
ELUM_KAKAO_NATIVE_APP_KEY=
ELUM_NAVER_CLIENT_ID=
ELUM_NAVER_CLIENT_SECRET=
ELUM_NAVER_CLIENT_NAME=이룸
ELUM_GOOGLE_SERVER_CLIENT_ID=     # ← 안드로이드 ID가 아니라 웹 클라이언트 ID
ELUM_GOOGLE_IOS_CLIENT_ID=
```

배포용 값은 `CLIENT_ENV_FILE` Secret에 `.env` **전체 내용**을 넣는다.
CI가 그 내용을 그대로 `.env`로 떨군다.

> `.env`는 커밋하지 않는다(`client/.gitignore`에 등록돼 있다).
> 새 키를 추가하면 `.env.example`과 `AppConfig`를 **함께** 고친다.

### 6-3. `.env`로 해결되지 않는 값 — 네이티브 설정 파일

로그인 후 앱으로 돌아오는 **URL 스킴은 빌드 타임에 필요해서 `.env`로 주입할 수 없다.**
아래는 파일에 직접 적어야 한다.

| 파일 | 넣을 것 |
|---|---|
| `client/android/app/src/main/AndroidManifest.xml` | 카카오 리다이렉트 스킴 `kakao{네이티브앱키}` (host `oauth`) |
| `client/ios/Runner/Info.plist` | 카카오 스킴 `kakao{네이티브앱키}`, 네이버 URL Scheme, 구글 reversed client ID |
| `client/ios/Runner/Info.plist` | `LSApplicationQueriesSchemes`에 `kakaokompassauth`, `naversearchapp` 등 |

카카오 네이티브 앱 키는 **비밀이 아니다.** 앱에 포함되는 공개 값이라
AndroidManifest에 적어도 보안 문제가 되지 않는다(비밀은 Admin 키뿐).

## 7. 앱(Flutter)에서 쓸 패키지

서버가 받는 것은 제공자 토큰 하나뿐이라, 앱은 SDK로 로그인만 하면 된다.

| 제공자 | 패키지 | 앱에 필요한 키 |
|---|---|---|
| 카카오 | `kakao_flutter_sdk_user` | 네이티브 앱 키 |
| 네이버 | `flutter_naver_login` | Client ID, Client Secret, URL Scheme |
| 구글 | `google_sign_in` | `serverClientId` = **웹 클라이언트 ID** |
| 애플 | `sign_in_with_apple` | 없음 (Capability만) |

### 서버로 보내는 형식

```
POST /api/auth/oauth/{provider}      provider = kakao | naver | google | apple
X-Device-Id: <기기 식별자>            (선택)

{ "token": "<제공자 SDK로 받은 토큰>" }
```

- 카카오·네이버 → **액세스 토큰**
- 구글·애플 → **ID 토큰(JWT)**

응답은 아이디/비밀번호 로그인과 같다.

```json
{
  "accessToken": "...",
  "tokenType": "Bearer",
  "expiresIn": 86400000,
  "refreshToken": "..."
}
```

`refreshToken`은 Keychain/Keystore 같은 안전한 저장소에 넣는다.
`accessToken`이 만료되면 `POST /api/auth/refresh`로 갱신하는데,
**갱신할 때마다 refreshToken도 새 값으로 바뀌므로 반드시 덮어써야 한다.**
옛 값을 다시 보내면 탈취로 간주해 그 계정의 모든 세션이 끊긴다.
동시에 여러 번 호출하지 않도록 갱신 요청은 한 번만 나가게 묶어야 한다.
