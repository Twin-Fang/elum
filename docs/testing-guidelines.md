# 테스트 설계 가이드라인

클라이언트(Flutter)와 서버(Spring Boot)가 같이 따른다. 모듈별 도구·헬퍼 사용법은
[client/CLAUDE.md §6](../client/CLAUDE.md)과 [server/CLAUDE.md](../server/CLAUDE.md)에 있다.

## 한 문장 원칙

**테스트는 결함 하나를 겨눈다.** 테스트를 쓰기 전에 이 문장을 먼저 채운다.

> "이 테스트가 깨지면 ___한 사용자 문제가 생긴다."

빈칸을 못 채우면 그 테스트는 쓰지 않는다. 채운 문장은 테스트 이름이나 한 줄 주석으로 남긴다.

테스트가 많다고 안전하지 않다. 2026-10 정리 전 클라이언트 테스트는 281개 파일, 5만 7천 줄이었다.
그중 상당수가 화면 문구를 그대로 베끼거나 끝난 이전 작업을 확인하는 테스트였다.
문구 하나 바꿀 때마다 깨지고 실제 결함은 잡지 못하면서 전체 실행만 무겁게 했다.

## 설계 절차 — 기능 하나를 만들 때

설계 문서(`docs/superpowers/specs/`)에 아래 순서로 적는다.

1. **실패 시나리오를 먼저 나열한다.** 네트워크 실패, 빈 응답, 형식 오류, 권한 거부, AI 실패,
   0건. 행복 경로는 그 다음이다.
2. **시나리오마다 가장 싼 층을 고른다.** (아래 표)
3. **이미 덮은 테스트가 있는지 찾는다.** 있으면 그 파일에 케이스를 더한다. 새 파일은
   기능(화면·서비스) 하나에 하나다.
4. **테스트를 먼저 쓰고 실패하는 것을 본다.** (TDD)
5. **구현 뒤에는 구현을 일부러 한 번 망가뜨려 본다.** 조건을 뒤집거나 줄을 지워도
   테스트가 통과하면 그 테스트는 아무것도 지키지 않는다. 고치거나 지운다.

### 층 선택

| 결함 성격 | 층 | 비용 |
|---|---|---|
| 값·변환·분기·계약(enum `apiValue`, JSON 필드, 에러 코드) | 단위 테스트 | ms |
| 버튼 활성 조건, 실패 시 화면, 빈 상태, 이동 | 위젯 테스트 / `@WebMvcTest` | 수백 ms |
| 트랜잭션·쿼리·스키마 | `@DataJpaTest` / 통합 테스트 | 초 |
| 구조 규칙(한글 리터럴 금지, 도메인 경계, 라우트 불변식) | 정적 검사 또는 전수 테스트 **하나** | 한 번 |
| 렌더 픽셀·시안 일치 | 골든·`figma_conformance` (`golden` 태그) | 무겁다 |
| 실제 기기·네트워크·권한·OS | 실기기 (`/pro-agent-test`) | 위젯 테스트로 대신하지 않는다 |

**싼 층에서 잡을 수 있는 결함을 비싼 층에서 잡지 않는다.** 조사 처리 로직은 함수 단위로
검증하고, 화면 테스트는 그 함수가 화면에 연결됐는지만 본다.

## 무엇을 단언하는가

| 단언한다 | 단언하지 않는다 |
|---|---|
| 서버로 가는 값, 서버에서 오는 값의 해석 | 화면 문구를 통째로 베낀 문자열 (로직이 없는 문구) |
| 사용자가 보는 결과 — 도착한 화면, 보이는 에러 코드, 활성/비활성 | 위젯 트리 구조, 위젯 개수, private 메서드 |
| 상태 전이 — 실패하면 재시도, 0건이면 빈 상태 | 가짜(mock)가 돌려준 값을 그대로 다시 확인 |
| 불변식 — 모든 상태 × 모든 경로 | `verify(mock).called` 만 있고 결과 단언이 없는 것 |
| 과거 결함의 재발 | 프레임워크·라이브러리 자체의 동작 |
| 원칙 위반 — 원문 비저장, 승인 전 노출 금지, fallback | getter·생성자만 부르는 것 |

문구는 **로직이 있을 때만** 문장 전체를 단언한다 (조사 `을/를`, 숫자·이름 끼워 넣기,
글자 수 제한). 그 밖에는 "그 자리에 문구가 있다"(키를 읽는다)까지만 본다.

계약 단언과 문구 단언을 한 테스트에 섞지 않는다. 섞이면 문구 단언만 지우기 어렵다.

### 가짜(mock)를 쓸 때

가짜는 **바깥 경계**(HTTP, 저장소, OS 채널, AI)에만 둔다. 가짜가 돌려준 값을 화면이 어떻게
**바꿔서** 보여주는지를 단언한다. 가짜가 정답을 쥐고 있으면 테스트는 가짜만 검증한다.

위젯 테스트가 통과해도 실패 경로는 실기기에서 한 번 밟는다. 위젯 테스트 769개가 통과한 뒤
실기기에서 결함 넷이 나온 적이 있다.

## 퇴역 — 테스트를 지우는 때

| 상황 | 처리 |
|---|---|
| 이전·마이그레이션을 확인하던 테스트 | 작업이 끝나면 지운다. 계속 지킬 규칙이면 정적 검사 하나로 바꾼다 |
| 기능이 사라짐 | 같은 PR에서 테스트도 지운다 |
| 다른 테스트가 같은 결함을 이미 잡음 | 싼 쪽을 남기고 지운다 |
| 문구만 베낀 단언 | 지운다. 계약 단언이 섞여 있으면 계약만 남긴다 |
| 과거 결함의 회귀 테스트 | **남긴다.** 이름에 어떤 결함을 막는지 적는다 |

지우기 전에 "이 테스트만 잡는 결함이 있는가"를 확인한다. 있으면 그 단언만 남긴다.

## 실행 예산

| 언제 | 무엇 | 명령 |
|---|---|---|
| 작업 중 | 건드린 파일의 테스트만 | `flutter test test/<파일>` / `./gradlew test --tests <클래스>` |
| 커밋 전 | 골든 뺀 전체 (CI 와 같은 조건) | `flutter test --exclude-tags golden` / `./gradlew test` |
| 배포 전 · 화면을 바꿨을 때 | 골든 포함 전체 1회 | `flutter test` |

### 클라이언트 테스트가 시간을 쓰는 곳 (2026-10 측정)

`flutter test --reporter json` 으로 쟀다. 12코어에서 전체 234초, CPU 합 1390초였다.

| 어디에 | CPU | 뜻 |
|---|---|---|
| **파일 로딩(컴파일)** | 784초 (56%) | 테스트 파일마다 따로 컴파일한다. 파일 하나에 평균 2.8초 |
| 테스트 실행 | 603초 (44%) | 화면을 띄우는 위젯 테스트가 대부분 |

그래서 아래를 지킨다.

- **새 파일보다 기존 파일에 케이스를 더한다.** 파일 하나가 늘 때마다 테스트가 비어 있어도 2.8초가 든다.
- 테스트 하나가 **2초를 넘으면** 원인을 찾는다. 대개 실제 파일 I/O 반복, 실제 타이머, 큰 화면을 언어·기기 크기별로 반복하는 루프다.
  예: 로그 파일 상한 테스트가 1KB 줄을 2500번 덧붙여 28초가 걸렸다. 50KB 줄 50번으로 같은 동작을 1초 안에 검증한다.
- 픽셀 비교(`matchesGoldenFile`)는 반드시 `@Tags(['golden'])` 를 붙인다. CI 와 평소 실행에서 빠진다.
- 테스트 파일 하나가 **500줄을 넘으면** 중복을 의심하고 나눈다.
- 여러 세션이 동시에 작업하므로 **전체 테스트는 마지막에 한 번만** 돌린다. 병렬 에이전트는 analyze까지만 한다.

## 리뷰 체크리스트 — 테스트가 들어간 PR

- [ ] 테스트마다 "깨지면 어떤 사용자 문제인가"가 이름이나 주석에 있다
- [ ] 실패 경로 테스트가 행복 경로만큼 있다
- [ ] 화면 문구를 통째로 베낀 단언이 없다 (로직 있는 문구 제외)
- [ ] 가짜가 돌려준 값을 그대로 단언하지 않는다
- [ ] 같은 결함을 이미 잡는 테스트를 새 파일로 또 만들지 않았다
- [ ] 픽셀 비교 테스트에 `golden` 태그가 있다
- [ ] 새 테스트 파일을 만들었다면, 기존 파일에 넣을 수 없었던 이유가 있다
